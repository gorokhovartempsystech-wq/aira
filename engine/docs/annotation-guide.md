# Правила разметки: изменение → противоречия

Черновик от 04.10.2026. Ответы на пять открытых вопросов гипотезы взяты
из рекомендаций разбора 29.09 и **ещё не утверждены научным руководителем**.
После утверждения правила замораживаются до прогона на test.

## Единица разметки

Пакет — набор связанных требований одного продукта (семейство документов).
В пакете есть запросы на изменение. Для каждого изменения разметчик отмечает:

| Поле | Что это |
|---|---|
| `kind` | `contradicting` — изменение порождает противоречие; `correct` — не порождает (в том числе намеренная замена старой версии) |
| `contradicts` | требования, которые после изменения **действуют одновременно с ним и не могут выполняться вместе**, и дословная цитата-основание из каждого |
| `evidence` | требования, которые эксперт хотел бы видеть, чтобы принять решение: противоречащие + исключения и связанные, которые меняют вывод |

## Что считается противоречием

Два требования **действуют одновременно** и **не могут выполняться вместе**
ни при какой разумной реализации.

- «Вернуть товар можно 30 дней» и «через 14 дней заявка отклоняется» — противоречие.
- «Отмена брони через 10 минут» и «напоминание через 10 минут, пока бронь действует» — противоречие без разных чисел: ловит только смысловая проверка.

**Не противоречие:**

- Старая версия (`deprecated`): «14 дней» в архивном регламенте — это замена версии, а не конфликт.
- Исключение (`exception`) со своей областью: «товары со скидкой — 7 дней» не противоречит «30 дням» для остальных.
- Обсуждение (`discussion`): «обсуждается 60 дней» — ещё не правило.
- Похожий, но другой параметр: «деньги возвращаются за 7 дней» и «товар можно вернуть за 30 дней».
- Дубль — отдельный тип, не противоречие.

## Статусы и связи

У каждого требования в пакете обязательно: `status` (`active` / `deprecated` / `exception` / `discussion`),
`version`, `section`, `document`. Явные связи — в `links`: ссылка по ID или по разделу.
Если в исходном документе статуса нет, разметчик ставит его по тексту и пишет основание в `note`.

## Процедура

1. Разметчики размечают **независимо**, не видя ответов модели и друг друга.
2. Согласие — каппа Коэна по парам «изменение — требование», порог **κ ≥ 0,7**.
3. Расхождения обсуждаются, решение и причина пишутся в `note`.
4. Правила дописываются только по итогам dev; на test — не меняются.

## Разбиение и объём

- dev / test — **по семействам документов**, не по изменениям: исходный текст и его варианты всегда в одной части.
- Цель для test: ≈ 140 эталонных противоречий и ≥ 30 корректных изменений, ≥ 20 семейств.
  Если не набирается — вывод сужается заранее («оценка на N семействах»).
- Синтетические пакеты помечены `source: synthetic`; выводы о реальных документах на них не обобщаются.
