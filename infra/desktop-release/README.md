# DESKTOP-RELEASE-01 — автоматический выпуск AIRA

Решение Никиты в чате 14 ноября 2026: после слияния изменений приложения в `main`
автоматически собирать Windows x64 и macOS Apple Silicon, проверять, подписывать
и публиковать установщики и каналы обновлений. Сайт получает актуальные ссылки
из отдельного публичного `updates/releases.json`, поэтому публикация HTML из
старого коммита не возвращает ссылки на прежние установщики.

## Состав процесса

Workflow `.github/workflows/desktop-release.yml` запускается для изменений
`app/**`, `engine/**`, `tools/**`, инфраструктуры публикации и самого workflow.
PR выполняет проверки и нативные сборки без доступа к ключу подписи и публикации.
Push в `main` или ручной Run workflow из `main` после успешных сборок подписывает
и публикует обе платформы. Общая группа для main сериализует выпуски;
запущенная публикация не отменяется при следующем merge. PR имеют отдельные
группы с отменой устаревших проверок и не могут отменить публикацию main.

Проверки: тесты движка, политики подписи и публикации, ограничения метаданных
сайта, контракты Windows-лицензирования и обновлений. Windows собирает staging,
проверяет launcher, создаёт EXE, устанавливает его и запускает дважды на одном
новом профиле. Mac запускает существующий полный backend gate с новым
socket-only PostgreSQL 18, собирает DMG, проверяет codesign/hdiutil и дважды
запускает runtime из DMG до активации. Это не полный пользовательский проход
с действующим ключом, анализом, редактированием и установкой updater поверх
предыдущей версии. Нативная проверка этих сценариев остаётся отдельной приёмкой;
существующие проверки закрытия и сохранения выполняются до публикации.

Сборка берёт код текущего checkout. Старые установщики используются только как
закреплённый источник Python/PostgreSQL; их app/backend/frontend не копируются.
Модель поставляется зашифрованной; каждый исходный архив проверяется по SHA-256.
Закреплённые архивы один раз загружаются отдельным Mac job и передаются через
GitHub Artifacts: это устраняет медленный прямой маршрут Windows runner к серверу.
Каждая сборка независимо повторяет SHA-256-проверку полученных архивов.
Отсутствие защиты модели в checkout блокирует выпуск. PR #42 уже объединён
с `main`: выпуск включает рассмотренные desktop-изменения и актуальные DOCX-исправления.

Автоматическая версия — `0.3.<GITHUB_RUN_NUMBER>`, Mac build —
`1000000 + GITHUB_RUN_NUMBER`. Ветка `0.3.*` зарезервирована этим workflow;
номер выше 65535 блокируется. Установщики имеют неизменяемые URL, повторная
публикация иных байтов под тем же именем запрещена. Повторить неудачный publish
job можно с прежними артефактами. Для полной новой сборки после опубликованного
выпуска используйте новый Run workflow, получающий новый номер.

## Подпись и доступ

Оператор один раз сохраняет **существующий** `AIRA_UPDATE_ED25519_SEED` в GitHub
Actions Secrets этого репозитория через `provision_secret.py`. Ключ проверяется
против встроенного открытого ключа перед загрузкой, шифруется sealed box GitHub
и никогда не выводится. Токен `GITHUB_TOKEN` нужен только этому операторскому
действию; после него токен можно отозвать. Источник — `~/secrets.env`. Для скрипта
нужны python-dotenv, cryptography и PyNaCl; ничего глобально устанавливать не нужно.

Ключ используется только отдельным publish job из `main`, после обеих сборок.
На одноразовом runner он помещается в его `~/secrets.env` с правами 0600 для
официального Sparkle signer и удаляется в finally. Ключ не попадает в артефакты,
установщики или сервер скачивания. Он не заменяется при обычном выпуске.
Подпись установщика независимо сверяется с публичным ключом перед загрузкой.
Mac appcast также подписан официальным Sparkle tool.

Сервер принимает короткоживущий GitHub OIDC-токен только для точного workflow
`desktop-release.yml@refs/heads/main`, фиксированных ID владельца/репозитория,
audience и main push/workflow_dispatch. Pull request и другой workflow доступа
не получают. Повторно используется валидатор OIDC сайта с отдельными параметрами;
его прежние настройки по умолчанию сохранены и проверены регрессиями.

## Сервер и переключение каналов

Отдельный пользователь `aira-release-publish`, root-owned код и venv в
`/opt/aira-release-publish`, состояние в `/var/lib/aira-release-publish`.
Сервис слушает только `127.0.0.1:8769`; Caddy проксирует три точных POST-маршрута
`/_deploy/releases/artifact/windows-x64`, `/_deploy/releases/artifact/macos-arm64`
и `/_deploy/releases/promote`. Публичная выдача добавляет только
`/updates/releases.json`; остальные маршруты сохраняются оператором.

Артефакты сначала загружаются потоком в непубличный staging; проверяются размер,
SHA-256 и источник. При promote сервер проверяет обе платформы, версии, commit,
публичные URL, Ed25519 каждого установщика и подпись Mac appcast. Только после
всех проверок установщики появляются в downloads с неизменяемыми именами.
Два appcast и releases.json переключаются через одну атомарную ссылку `current`.
Старый запуск не может заменить новый; старые каталоги и установщики сохраняются.
При недостатке места выпуск останавливается, старые файлы автоматически не удаляются.

Процесс не имеет прав на базу лицензий, её настройки и Caddy. Записываемые пути
ограничены собственным состоянием и downloads. Секретов в сервисе нет.
Публичные appcast/release JSON указывают через `current`; ручная замена этих
ссылок обычными файлами нарушает публикацию. Публикуйте через workflow.

После promote job проверяет публичные feeds, JSON и размер обоих установщиков
по HTTPS. Ошибка проверки делает job красным. Уже переключённый выпуск не
понижается автоматически: оператор сверяет receipt и при необходимости
возвращает ссылку `current` на предыдущий каталог. Уже установленные приложения
автоматически на более старую версию не переводятся.

## Границы

Подпись Ed25519 подтверждает происхождение обновлений; она не заменяет Apple
Developer ID/notarization и Microsoft Authenticode. Эти сертификаты у команды
пока отсутствуют, workflow их не имитирует. Intel Mac, Windows ARM, модель
нового формата и изменение ключа подписи требуют отдельного решения.

Техническая проверка:

```sh
python -m unittest discover -s infra/desktop-release -p 'test_*.py' -v
python -m unittest discover -s infra/site-deploy -p 'test_*.py' -v
node infra/desktop-release/test_site.mjs
```

Начальная настройка сохраняет действующие feeds и конфигурацию Caddy в закрытой
резервной папке на сервере. Сначала готовятся код и тесты, затем валидируется
Caddy и включается отдельный сервис. Работающий сайт и лицензирование проверяются
после установки. Ключ подписи для этой настройки серверу не нужен.
