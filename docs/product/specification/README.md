# Спецификация AIRA: MVP для пилотного использования

> Текстовая копия исходного документа от 4 ноября 2026 года. Формулировки требований сохранены; предложения не внесены в основной текст. Заявленный в исходнике статус не является подтверждением реализации или согласования этого PR.

Исходник: [DOCX](specification-2026-11-04.docx). Обсуждение: [предложения к спецификации](proposals.md).

Версия документа: 1.0Статус: согласованная функциональная основа; открытые вопросы отмечены отдельноЦелевые платформы: Windows и macOS

## 1. Назначение документа

Спецификация определяет требования к пилотной версии AIRA — локального редактора требований со встроенной нейросетью для AI-ревью.

Документ объединяет:

функции существующего браузерного прототипа, описанные по результатам анализа бэкенда;

согласованные изменения для пилотной версии;

требования к интерфейсу;

правила хранения, сохранения и восстановления данных;

ограничения и открытые вопросы.

Важно: описание существующей реализации основано на предоставленном перечне функций прототипа engine/aira_ml/proto.py. Исходники в рамках подготовки этой спецификации не проверялись. Соответствие реализации требованиям необходимо подтвердить отдельно.

## 2. Назначение продукта и пользователи

### 2.1. Основной пользователь

Системный аналитик, который пишет и проверяет текстовые требования.

### 2.2. Основная задача

Помочь пользователю выполнить ревью документа:

найти проблемные формулировки;

обнаружить возможные смысловые дубли;

выявить возможные противоречия;

получить вопросы при недостатке контекста;

перейти от замечания к соответствующему фрагменту;

вручную исправить документ и повторить проверку.

Создание требований с нуля поддерживается, но основной сценарий пилота — ревью существующего документа.

### 2.3. Принцип работы AI

Нейросеть читает документ и формирует замечания и вопросы.

Нейросеть не изменяет текст документа, не применяет исправления и не сохраняет документ вместо пользователя. Все изменения пользователь вносит самостоятельно.

## 3. Границы MVP

### 3.1. Входит в пилот

Устанавливаемое локальное приложение для Windows и macOS.

Поставка модели вместе с приложением.

Работа одного пользователя без ролей и отдельной авторизации.

Создание документа с нуля и открытие DOCX.

Визуальный текстовый редактор.

Вкладки открытых документов.

Панель недавних документов.

Ручное сохранение и история ручных версий.

Автоматическая восстановительная копия для защиты от сбоя.

AI-ревью одного документа за раз.

Подсветка проблемных фрагментов.

Фильтрация замечаний по критериям.

AI-вопросы и сохранение ответов как контекста.

Сохранение последних результатов проверки.

Копирование текста и экспорт DOCX.

Активация лицензии.

### 3.2. Не входит в пилот

Дерево папок и проектов внутри AIRA.

Перемещение и копирование документов между папками средствами приложения.

Междокументный анализ.

Одновременные проверки нескольких документов.

Совместное редактирование.

Роли пользователей.

Автоматическое применение AI-исправлений.

Массовое исправление замечаний.

Изменение весов модели на ответах пользователя.

Импорт и экспорт Markdown.

Импорт PDF.

Отчёт с AI-замечаниями.

Корзина документов.

Сравнение версий.

Телеметрия и автоматическая отправка диагностических данных.

Автоматическое обновление через приложение.

Мобильный интерфейс.

Перенос файлов между компьютерами выполняется вне AIRA, средствами операционной системы.

## 4. Установка, запуск и локальная работа

### ENV-01. Поддерживаемые платформы

Приложение должно поддерживать Windows и macOS.

Поддерживаемые версии ОС и архитектуры процессоров определяются до выпуска пилотной сборки.

### ENV-02. Дистрибутив

Дистрибутив должен содержать компоненты приложения и совместимый пакет модели, необходимые для AI-ревью.

Пользователь не должен самостоятельно искать и подключать веса модели для штатного запуска.

### ENV-03. Локальная обработка

Документы, AI-замечания, ответы пользователя, контекст и история должны обрабатываться и храниться локально.

Передача этих данных внешним сервисам запрещена.

### ENV-04. Сетевые обращения

Разрешены только обращения, необходимые для лицензирования.

Скачивание моделей, телеметрия, проверка обновлений и другие сетевые обращения не должны выполняться без изменения этого требования.

### ENV-05. Проверка модели при запуске

При запуске приложение должно проверить наличие и совместимость пакета модели.

При недоступности модели:

редактор и доступ к документам остаются доступны;

AI-ревью отключается;

пользователь видит объяснение проблемы.

Наличие пакета модели и готовность вычислительного процесса к проверке считаются разными состояниями. Подготовка модели может выполняться при запуске AI-ревью.

### ENV-06. Недостаток ресурсов

Если приложение может определить нехватку ресурсов, оно должно показать понятное уведомление.

Ошибка модели или нехватка ресурсов не должны приводить к намеренной блокировке сохранения пользовательского документа.

## 5. Основной пользовательский сценарий

Пользователь устанавливает приложение.

Выполняет активацию лицензии.

Создаёт документ, открывает DOCX или выбирает документ из недавних.

Редактирует текст.

При необходимости вручную сохраняет документ.

Запускает AI-ревью.

Видит подготовку модели, этап проверки и время выполнения.

Дожидается результата либо останавливает проверку.

Разбирает замечания и вопросы.

Переходит от карточек к фрагментам документа.

Вносит исправления вручную.

При необходимости отвечает на AI-вопросы.

Повторно запускает полную проверку.

Сохраняет документ или экспортирует его в DOCX.

При следующем запуске возвращается к документу и последним результатам.

## 6. Структура интерфейса

### UI-01. Основной экран

Основной экран должен содержать:

| Область | Содержимое |
| --- | --- |
| Верхняя панель | Название документа, сохранение, форматирование, история версий, основные действия |
| Вкладки | Открытые документы |
| Левая раскрываемая панель | Недавние документы |
| Центральная область | Редактор и оглавление |
| Правая панель | «ИИ-замечания» и «ИИ-вопросы» |
| Нижняя область | Кнопка запуска AI-ревью и состояние проверки |

### UI-02. Темы

Должны поддерживаться светлая и тёмная темы.

### UI-03. Размер панелей

Пользователь должен иметь возможность изменять ширину боковых панелей.

### UI-04. Область применения

Интерфейс проектируется для настольных компьютеров.

Отдельное управление масштабом текста не требуется. Изменение параметров шрифта предусмотрено средствами редактора.

## 7. Документы и навигация

### DOC-01. Создание документа

Пользователь должен иметь возможность:

создать пустой документ;

создать учебный документ с примером требований.

### DOC-02. Открытие документа

Приложение должно поддерживать открытие DOCX.

Markdown не входит в пилот.

### DOC-03. Вкладки

Открытые документы должны отображаться во вкладках.

Одновременно редактируется один активный документ.

Открытие нескольких вкладок не означает анализ связей между документами.

### DOC-04. Недавние документы

В раскрываемой панели слева должен отображаться список недавних документов.

Пользователь должен иметь возможность:

открыть документ из списка;

убрать документ из списка.

Удаление из недавних не должно удалять файл с компьютера или историю документа.

### DOC-05. Закрытие вкладки

Закрытие вкладки убирает представление документа из текущего интерфейса, но не удаляет документ из недавних.

При наличии изменений, не сохранённых вручную, должен применяться диалог сохранения.

### DOC-06. Восстановление рабочего состояния

Между запусками приложение должно запоминать:

открытые вкладки;

активный документ.

При восстановлении должны учитываться доступность исходных файлов и наличие восстановительных копий.

### DOC-07. Переименование

Переименование сохранённого документа должно менять имя реального файла.

Если операция не выполнена, приложение не должно показывать новое имя как успешно сохранённое.

### DOC-08. Отсутствующий файл

Если исходный файл не найден, приложение должно:

сообщить об этом;

предложить указать новое расположение;

предложить открыть последнюю доступную внутреннюю копию, если она существует.

### DOC-09. Внешнее изменение

Если файл изменён другой программой после последнего известного состояния, приложение не должно молча перезаписывать его.

Пользователю должен быть предложен выбор между актуальным файлом с диска и внутренней копией AIRA.

Сравнение версий в пилоте не требуется.

### DOC-10. Удаление

Корзина и удаление реального файла средствами AIRA не требуются.

Удаление документа из списка недавних является отдельной операцией и не затрагивает файл.

## 8. Редактор

### EDT-01. Редактирование

Пользователь должен иметь возможность изменять название и содержимое документа.

### EDT-02. Форматирование

Редактор должен предусматривать:

заголовки;

абзацы;

маркированные и нумерованные списки;

жирное начертание;

настройку шрифта;

таблицы;

ссылки;

изображения.

Точный перечень поддерживаемых параметров и ограничений должен быть согласован в матрице поддержки DOCX.

### EDT-03. Отмена и повтор

Редактор должен поддерживать отмену и повтор действий.

### EDT-04. Поиск

По сочетанию Ctrl+F должен открываться поиск по текущему документу.

Для macOS необходимо определить эквивалентные сочетания клавиш.

### EDT-05. Оглавление

Оглавление должно строиться по заголовкам документа и позволять переходить к соответствующим разделам.

### EDT-06. Счётчики

Должны отображаться количество символов и количество строк.

Правила подсчёта строк в визуальном редакторе требуют уточнения.

### EDT-07. Подсветка замечаний

Проблемные фрагменты должны выделяться непосредственно в документе.

Подсветка является элементом интерфейса и не должна включаться в экспортируемый DOCX.

### EDT-08. Переход к фрагменту

При нажатии на цитату в карточке приложение должно плавно прокручивать редактор к соответствующему фрагменту и визуально обозначать его.

### EDT-09. Блокировка при проверке

Во время проверки:

редактирование проверяемого документа блокируется;

переключение на другой документ блокируется;

повторный запуск проверки блокируется;

отображается индикатор выполнения.

Левая панель недавних не должна перекрываться общим лоадером, однако открытие другого документа до завершения или остановки проверки недоступно.

Текст индикатора может быть сформулирован как:

Подождите ещё чуть-чуть, проверяем документ.

Этап подготовки модели должен обозначаться отдельно.

### EDT-10. Представления документа

Markdown как формат импорта и экспорта исключён.

Необходимость отдельного режима отображения разметки после исключения Markdown остаётся открытым вопросом. До его разрешения нельзя считать обязательным переключение между визуальным редактором и Markdown-режимом.

## 9. Импорт и сохранение DOCX

### FMT-01. Открытие DOCX

При открытии приложение должно преобразовать поддерживаемое содержимое DOCX во внутреннее представление документа.

### FMT-02. Неподдерживаемые элементы

Если обнаружены неподдерживаемые элементы:

пользователь должен получить предупреждение;

приложение должно объяснить возможные изменения содержимого;

неподдерживаемое содержимое по возможности преобразуется в согласованное понятное представление.

Недопустимо обещать полное сохранение всех элементов DOCX без утверждённой матрицы поддержки.

### FMT-03. Сохранение в исходный файл

Если документ обработан без потерь поддерживаемого содержимого, приложение должно позволять сохранить изменения в исходный файл.

### FMT-04. Сохранение после преобразования с потерями

Если обнаружены неподдерживаемые элементы или выполнено преобразование с потерями, приложение должно предупреждать об этом и по умолчанию предлагать «Сохранить как…».

### FMT-05. Экспорт

Экспортируется текущий документ с изменениями, которые пользователь внёс вручную.

В экспорт не включаются:

AI-замечания;

AI-вопросы;

служебная подсветка;

контекст ответов;

история версий.

### FMT-06. Копирование

Пользователь должен иметь возможность скопировать текст документа в буфер обмена.

### FMT-07. Ошибка записи

Если файл недоступен для записи, приложение должно:

сохранить возможность продолжить работу;

показать ошибку;

предложить повторить сохранение или выбрать другое расположение.

Статус «Сохранено» допускается только после успешного завершения соответствующей операции.

## 10. Хранение данных и идентификация

### DAT-01. Внутренний формат

Рабочее представление документа должно храниться локально в JSON.

Структура JSON должна поддерживать согласованные элементы документа и служебные идентификаторы.

### DAT-02. Идентификатор документа

Каждому документу должен присваиваться постоянный внутренний document_id.

Переименование файла не должно создавать новый документ в истории AIRA.

Идентификатор не обязан записываться внутрь пользовательского DOCX.

### DAT-03. Разделение данных

Приложение должно разделять:

пользовательский DOCX;

внутреннее представление документа;

восстановительную копию;

ручные версии;

результаты проверки;

ответы пользователя и контекст;

правила скрытия замечаний и вопросов.

### DAT-04. Служебное хранилище

Служебные данные должны размещаться в пользовательской папке данных AIRA, отдельно от исходного DOCX.

Логическая структура:

text

AIRA/

├── registry

└── documents/

    └── <document_id>/

        ├── metadata

        ├── working-copy

        ├── manual-versions/

        ├── last-review

        ├── context

        └── suppression-rules

Конкретная файловая структура может отличаться при сохранении указанного логического разделения.

### DAT-05. Метаданные

Для документа необходимо хранить как минимум:

ID;

отображаемое имя;

путь к исходному файлу, если он задан;

формат;

текущую ревизию;

последнюю успешную ручную версию;

сведения для определения внешнего изменения;

время последнего открытия и сохранения.

### DAT-06. Перенос документов

Перенос файлов выполняется вне приложения.

Автоматическое распознавание перемещённого файла не является обязательной функцией пилота. Должен поддерживаться сценарий указания нового пути.

Перенос истории, контекста и результатов между компьютерами не считается автоматически обеспеченным переносом DOCX.

## 11. Ручное сохранение и защита от сбоя

### SAV-01. Ручное сохранение

Ручное сохранение должно быть доступно:

кнопкой в верхней панели;

сочетанием Ctrl+S;

соответствующим сочетанием для macOS.

Для нового документа приложение запрашивает имя и расположение файла.

### SAV-02. Восстановительная копия

Приложение должно автоматически сохранять внутреннюю рабочую копию для восстановления после сбоя.

Она не должна обновлять исходный DOCX.

### SAV-03. Назначение автоматической записи

Автоматическая запись предназначена для защиты от потери данных.

Отдельная история из 30 автоснимков не требуется.

Частота записи восстановительной копии остаётся открытым параметром.

### SAV-04. Состояния сохранения

Интерфейс должен различать:

наличие изменений, не сохранённых вручную;

ручное сохранение;

успешное ручное сохранение;

автоматическую запись восстановительной копии;

ошибку сохранения.

Наличие восстановительной копии не должно создавать впечатление, что исходный DOCX обновлён.

### SAV-05. Восстановление после сбоя

При обнаружении восстановительной копии, отличающейся от последнего ручного сохранения, приложение должно предложить:

восстановить рабочую копию;

открыть сохранённую версию;

удалить восстановительную копию.

Сравнение содержимого в пилоте не требуется.

### SAV-06. Закрытие приложения

Если текущее содержимое отличается от последнего успешного ручного сохранения, при закрытии должен появляться диалог:

«Сохранить»;

«Не сохранять»;

«Отмена».

«Сохранить» должно иметь более заметное визуальное оформление.

Если содержимое не отличается, диалог не показывается.

Автоматическая запись восстановительной копии не отменяет этот диалог.

### SAV-07. Семантика отказа от сохранения

Действие «Не сохранять» не обновляет исходный DOCX.

Правило дальнейшего хранения восстановительной копии после осознанного отказа пользователя от сохранения необходимо уточнить.

## 12. История версий

### VER-01. Ручные версии

Успешные ручные сохранения должны формировать историю версий документа.

### VER-02. Интерфейс истории

Пользователь должен иметь возможность:

открыть список ручных версий;

просмотреть выбранную версию;

восстановить её.

Сравнение версий не входит в MVP.

### VER-03. Восстановление версии

Восстановление должно создавать новую рабочую ревизию и новую запись истории восстановления.

Более поздние версии не должны удаляться вследствие восстановления старой.

Исходный DOCX обновляется только после ручного сохранения.

### VER-04. Ограничение истории

Предел хранения ручных версий остаётся открытым.

Прежний лимит в 30 записей не переносится на ручные версии автоматически.

### VER-05. Снимок для проверки

Каждая проверка должна относиться к зафиксированной ревизии документа.

Нужен ли отдельный доступный пользователю исторический снимок перед каждой проверкой, определяется при проектировании хранения.

## 13. AI-ревью

### AI-01. Область проверки

Каждый запуск выполняет полную проверку активного документа.

Проверка выделенного фрагмента и междокументный анализ не входят в пилот.

### AI-02. Язык

Основной язык — русский.

Документ может содержать англоязычные термины.

### AI-03. Предварительные категории

Предусматриваются категории:

| Категория | Назначение |
| --- | --- |
| Формулировка | Неопределённые слова, условия, незакрытые перечни |
| Возможный дубль | Близкие по смыслу фрагменты |
| Возможное противоречие | Потенциально несовместимые требования |
| Влияние правки | Связанные фрагменты, которые стоит перепроверить после изменения |

Подробные правила категорий и включение «Влияния правки» в пилот остаются открытыми.

### AI-04. Единица анализа

Единицей анализа является абзац либо явно выделенное в структуре документа требование, если такая структура предусмотрена.

Правила определения отдельных требований необходимо уточнить.

### AI-05. Запуск

Проверка запускается:

кнопкой «AI-ревью»;

сочетанием Ctrl+Enter;

соответствующим сочетанием для macOS.

### AI-06. Пустой документ

Запуск проверки пустого документа должен предотвращаться с понятным объяснением.

### AI-07. Единственная активная задача

Одновременно допускается только одна задача проверки.

Повторные нажатия не должны создавать дополнительные задачи.

### AI-08. Состояния проверки

Должны различаться:

подготовка модели;

выполнение анализа;

успешное завершение;

остановка пользователем;

превышение лимита;

ошибка.

### AI-09. Прогресс

Пользователь должен видеть:

текущий этап;

время с начала запуска;

достоверный показатель прогресса, если движок его предоставляет.

Если точный процент неизвестен, интерфейс должен показывать этап или счётчики, а не условное значение, выдаваемое за точное.

### AI-10. Лимит времени

Общий лимит составляет пять минут, включая подготовку модели.

При превышении лимита приложение должно завершить ожидание проверки и показать доступный частичный результат.

### AI-11. Частичный результат

Частичный результат должен явно отличаться от полного.

При наличии достоверной информации приложение показывает обработанные блоки или диапазоны строк отдельно для соответствующих проверок.

Нельзя обозначать весь документ проверенным только потому, что один этап дошёл до последней строки.

### AI-12. Остановка

Пользователь должен иметь возможность остановить проверку.

Уже полученные замечания сохраняются и отображаются как частичный результат.

### AI-13. Поздние результаты

После подтверждённой остановки набор результатов фиксируется.

Поздние ответы остановленной задачи не должны дополнять отображаемый результат или заменять результат новой проверки.

### AI-14. Ошибка

При ошибке приложение должно:

показать понятное сообщение;

сохранить доступ к документу;

предложить повторный запуск;

обозначить частичность уже полученных результатов, если они доступны.

### AI-15. Полное отсутствие замечаний

Сообщение «Замечаний не найдено» должно отличаться от состояния «Проверка не завершена».

Неполная проверка без найденных замечаний не должна представляться как успешное полное ревью.

### AI-16. Исключаемые статусы

Статусы «архивное», «черновое», «обсуждаемое» и исключение таких пунктов из проверки в пилоте не реализуются.

## 14. Замечания и фильтрация

### REV-01. Правая панель

Правая панель должна содержать переключение:

«ИИ-замечания»;

«ИИ-вопросы».

### REV-02. Карточка замечания

Карточка должна содержать:

один или несколько критериев;

цитату;

объяснение;

критичность;

связанную цитату, если она необходима для понимания проблемы.

Уверенность модели не показывается.

### REV-03. Оформление

Карточки должны иметь нейтральный серый фон с адаптацией к теме.

Для критичности используются красный, оранжевый и жёлтый индикаторы.

Названия уровней и правила назначения критичности остаются открытыми. Смысл индикатора должен быть понятен не только по цвету.

### REV-04. Фильтры

Должен быть общий фильтр со всеми замечаниями и отдельные фильтры по критериям.

### REV-05. Несколько критериев у одного фрагмента

Если к одному проблемному фрагменту относятся несколько критериев:

показывается одна объединённая карточка;

карточка содержит соответствующие метки;

карточка доступна в каждом соответствующем фильтре;

в общем списке она не дублируется.

Правила объединения должны сохранять объяснения всех относящихся к фрагменту проблем.

### REV-06. Связанные фрагменты

Для дубля и противоречия одна карточка должна показывать две связанные цитаты.

Каждая цитата должна позволять перейти к своему фрагменту.

### REV-07. «Принято»

Действие «Принято»:

убирает карточку из текущего списка;

снимает соответствующую подсветку;

не изменяет документ;

не запрещает повторное появление замечания при следующем ревью.

### REV-08. «Скрыть»

Действие «Скрыть»:

убирает карточку и её подсветку;

создаёт правило скрытия для повторных проверок;

не изменяет документ.

### REV-09. Идентификация скрытого замечания

Сопоставление должно учитывать документ, критерий, проблемный фрагмент и связанный фрагмент при его наличии.

Сопоставление только по дословному тексту объяснения недостаточно.

После существенного изменения текста правило скрытия должно пересматриваться.

Точные правила сопоставления требуют технической проработки.

### REV-10. Сброс скрытия

Должна быть возможность сбросить скрытые замечания для документа.

### REV-11. Актуальность

После изменения документа прежние результаты должны помечаться как устаревшие.

Если соответствующая цитата отсутствует, приложение не должно выполнять переход к неподтверждённому месту по случайному совпадению текста.

### REV-12. Привязка

Замечания должны связываться с:

ID документа;

проверенной ревизией;

блоком или абзацем;

диапазоном текста;

цитатой как дополнительным ориентиром.

Номер строки используется как вспомогательная информация.

## 15. AI-вопросы и контекст

### CTX-01. Назначение

AI-вопросы используются для уточнения недостающих условий и контекста документа.

Подробные правила отделения вопроса от замечания остаются открытыми.

### CTX-02. Отключение списка

Пользователь должен иметь возможность выключить отображение списка AI-вопросов.

Отключение отображения само по себе не означает удаления ранее сохранённых ответов.

### CTX-03. Ответ на вопрос

По нажатию на вопрос должна открываться область ввода ответа.

Ответ сохраняется локально и используется при следующем AI-ревью.

Автоматический запуск проверки после ответа не требуется.

### CTX-04. Отсутствие дообучения

Ответы не изменяют веса модели.

Они используются как дополнительный контекст для следующих проверок.

### CTX-05. Скрытие вопроса

Скрытый вопрос:

исчезает из списка;

не должен повторяться при последующих проверках;

не передаётся модели как контекст;

не передаёт связанный с ним ответ как контекст.

Служебная запись о скрытии хранится отдельно от контекста для модели.

### CTX-06. Файл контекста

Контекст должен храниться локально.

Возможность ручного удаления пользователем отдельных параметров из файла контекста требует технического подтверждения.

До реализации необходимо определить:

формат файла;

допустимые изменения;

обработку повреждённого содержимого;

отличие удаления ответа от отмены скрытия вопроса.

## 16. Последние результаты и повторное открытие

### RES-01. Сохранение результатов

Приложение должно сохранять последние результаты проверки документа.

Результат включает сведения о ревизии и состоянии завершения.

### RES-02. Повторное открытие

При открытии документа приложение должно восстанавливать доступные последние результаты и обозначать их актуальность.

### RES-03. Изменение файла

Если документ изменился после проверки, результаты не должны выглядеть актуальными.

### RES-04. Частичный результат

Признак частичной проверки должен сохраняться между запусками.

## 17. Лицензирование

### LIC-01. Активация

В пилоте должна быть предусмотрена активация лицензии на устройстве с привязкой к компьютеру.

### LIC-02. Сетевой доступ

Сетевые обращения допускаются только в рамках согласованного процесса лицензирования.

### LIC-03. Перенос

Перенос лицензии на другой компьютер находится на обсуждении. Предварительный вариант — ручная обработка через поддержку.

Автоматический перенос не входит в согласованные требования.

### LIC-04. Открытые вопросы

Не утверждены:

срок лицензии, включая гипотезу о годовом сроке;

необходимость периодической проверки;

допустимый срок автономной работы;

поведение при недоступности сервера;

поведение после окончания лицензии;

перечень передаваемых данных;

переактивация после переустановки ОС;

замена компьютера и восстановление активации.

Ограничение доступа к документам после окончания лицензии не считается согласованным требованием.

## 18. Безопасность и диагностика

### SEC-01. Локальные данные

Защита данных на старте опирается на средства защиты компьютера пользователя.

Отдельное шифрование хранилища AIRA в пилоте не требуется.

### SEC-02. Логи

Текст требований, ответы пользователя и содержимое документов не должны записываться в диагностические логи.

### SEC-03. Передача данных

Автоматическая передача документов, результатов, контекста и диагностических материалов запрещена.

### SEC-04. Диагностика

Разбор проблем пилота выполняется вручную через поддержку.

Передаваемые пользователем диагностические материалы должны предварительно проверяться на наличие чувствительных данных.

### SEC-05. Проверка импортируемых файлов

Перед обработкой необходимо проверять допустимость файла и применять технические ограничения ресурсов.

Числовые значения ограничений остаются открытыми.

### SEC-06. Безопасность сохранения

Реализация должна предусматривать защиту от повреждения существующих данных при незавершённой записи.

Конкретный механизм безопасной записи и восстановления определяется при техническом проектировании.

## 19. Обновление приложения

### UPD-01. Готовность сборки

Каждая распространяемая версия должна содержать совместимые компоненты приложения и модели.

### UPD-02. Сохранность данных

Обновление не должно удалять пользовательские документы, ручные версии, контекст и последние результаты.

При изменении внутреннего формата необходимо предусмотреть миграцию данных.

### UPD-03. Уведомления

В будущем уведомления о новых версиях планируется предоставлять через Telegram-бота.

Создание бота и автоматическое обновление не входят в текущий MVP.

## 20. Логический контракт фронтенда и движка

Конкретный способ взаимодействия — HTTP API, IPC или другой механизм — не утверждён.

Контракт должен поддерживать следующие сущности.

### 20.1. Документ

document_id;

название;

путь;

формат;

содержимое и структура;

текущая ревизия;

последняя ручная версия;

состояние сохранения.

### 20.2. Задача проверки

review_id;

document_id;

проверяемая ревизия;

статус;

этап;

время начала;

прогресс или счётчики;

частичный результат;

причина завершения;

сведения об ошибке.

### 20.3. Замечание

идентификатор;

критерии;

критичность;

объяснение;

один или несколько фрагментов;

привязка к ревизии;

состояние актуальности;

состояние принятия или скрытия.

### 20.4. Вопрос

идентификатор;

текст;

связь с документом и фрагментом при наличии;

ответ;

состояние скрытия;

признак включения ответа в контекст.

### 20.5. Основные операции

Контракт должен обеспечивать:

создание и открытие документа;

загрузку и сохранение содержимого;

управление недавними и вкладками;

переименование;

работу с восстановительной копией;

получение и восстановление ручных версий;

запуск, отслеживание и остановку проверки;

получение результатов;

принятие и скрытие замечаний;

сохранение ответов;

управление скрытыми вопросами;

экспорт DOCX.

Фронтенд не должен самостоятельно подменять успешное завершение операции предположением о её успехе.

## 21. Критерии приёмки основных сценариев

| Сценарий | Ожидаемый результат |
| --- | --- |
| Запуск без модели | Редактор доступен; AI-ревью отключено с объяснением |
| Открытие DOCX | Поддерживаемое содержимое доступно для редактирования; потери обозначены |
| Ручное сохранение | Файл успешно записан; создана ручная версия; статус обновлён |
| Ошибка записи | Нет ложного статуса «Сохранено»; изменения доступны для дальнейшей работы |
| Сбой после редактирования | При следующем запуске предлагается восстановительная копия |
| Выход с изменениями | Показан диалог сохранения независимо от наличия автокопии |
| Выход без изменений | Диалог сохранения не показывается |
| Запуск проверки | Редактор и переключение документов заблокированы; повторный запуск недоступен |
| Истечение пяти минут | Показан доступный частичный результат с явным признаком неполноты |
| Остановка | Полученные результаты сохранены; поздние ответы не меняют зафиксированный результат |
| Переход из карточки | Открывается соответствующий фрагмент документа |
| «Принято» | Карточка и подсветка убраны; текст не изменён |
| «Скрыть» | Замечание скрыто и подавляется при повторном обнаружении по согласованным правилам |
| Ответ на AI-вопрос | Ответ используется при следующем ревью без изменения весов модели |
| Экспорт | Получен DOCX с пользовательскими правками, без AI-замечаний и вопросов |
| Внешнее изменение файла | Нет молчаливой перезаписи; пользователю предложен выбор |
| Восстановление версии | Создана новая ревизия; существующая история сохранена |
