# Frontend и установщик Windows AIRA — передача изменений 16 ноября 2026

Сделаны интерфейс AIRA поверх готового API бэкенда и пилотный установщик для Windows
со встроенными Python, PostgreSQL и моделью. Позже в main исправлен запуск после
прерванной проверки. Backend и клиентские модули `/client` во всех этих изменениях
не менялись: правки только в `app/frontend`. Документ описывает, что сделано и
проверено. Это не новая продуктовая спецификация.

## Восстановление после прерванной проверки

Это главное исправление пилота. 8 ноября у пилотного пользователя AIRA 0.2.0
перестала запускаться и бесконечно показывала «Загружаем модель…».

- **Причина.** Выход нажали во время проверки, а потом ещё раз. Остановка воркера не
  уложилась в 30 с, и процесс завершился. Запись `docx_analysis_supervisor` осталась
  в `armed`, и бэкенд при каждом старте отвечал `recovery_required`. Супервизор
  стартует только из `clean` или `drained`.
- **Почему не помогала прежняя разблокировка.** Она срабатывала, только если прогон
  уже завершён (`succeeded/failed/cancelled/timed_out`). Здесь прогон остался `running`.
- **Что делает запускатель теперь.** Если старт отклонён с `recovery_required`, запись
  в `armed` и в системе нет других процессов Python из папки AIRA, запись переводится
  в `drained`. На Windows воркеры работают в Job с kill-on-close, поэтому без старого
  процесса AIRA их тоже нет. Дальше бэкенд восстанавливается штатно
  (retire → restore → probe → clear_old): прогон помечается `failed/interrupted`,
  документы и прошлые результаты сохраняются.
- **Если старые процессы живы**, запускатель ничего не трогает и пишет «Прошлый запуск
  AIRA ещё не завершился…».

Это обход во frontend. Правильнее, чтобы бэкенд сам восстанавливался после рестарта
на Windows. Пока такого нет, `stuck_fence` / `release_stuck_fence` в
`aira_launcher.pyw` удалять нельзя.

## Что нужно учесть команде

1. **Удаление документов.** В API бэкенда его нет. «Удалить» в списке «Недавние»
   только скрывает документ: идентификаторы хранятся в `localStorage`
   (`aira.hiddenDocs`), сам документ остаётся в базе. `localStorage` привязан к
   адресу, поэтому порт окна закреплён (`47017`, база `47432`). Если порт сменится,
   пользователи потеряют скрытые документы, масштаб, состояние панелей и пройденное
   обучение (обучение Никита с 14 ноября хранит в профиле).
2. **Элементы Word, на которых отказывала проверка.** До D03-20 бэкенд отказывал
   (`unsupported_analysis_content`) на мягком и неразрывном дефисе, `w:sym`, `w:ptab`,
   `m:oMath`, надписях VML, `pBdr` и `numPr` без `numId` в стилях. Frontend 0.1.2
   находил их сам и не давал запустить проверку. После D03-21A (`d2a3d71`) решение о
   допуске принимает бэкенд, а frontend только предупреждает
   («Поддержка зависит от содержимого элемента»). Список `BLOCKERS` в
   `docx-assets.mjs` остался прежним. Он нужен только для подсказки, и после D03-20B/C
   часть элементов в нём уже поддерживается.
3. **Файл Word для Mac, на котором падала проверка.** В отчёте backend от 9 ноября
   сказано, что оригинала у команды нет. Он есть: `QuickSlot_requirements_test.docx`
   есть у команды frontend. В нём два известных блокера и минимум одна неизвестная
   часть пакета. Если файл передать, сбой можно воспроизвести.
4. **Журнал для разработчиков.** Меню «?» → «Скачать журнал для разработчиков».
   Отдаёт `GET /aira/diagnostics/log` (только с токеном сессии). В журнал попадают
   запросы анализа, ответы с ошибками, ошибки страницы и шаги запуска.
5. **GitHub Actions.** С 15 ноября все проверки в репозитории падают за 1–2 с с
   сообщением о неоплаченном аккаунте владельца. До исправления оплаты тесты нужно
   гонять локально (раздел «Проверки»).

## Фактически проверенный сценарий

На Windows 10, с локальным PostgreSQL 18 и настоящим пакетом `models-0.2m`:

- смоук-страницы dev-стенда `/aira/dev-pages/smoke.html?s=…`: создание, сохранение,
  закрытие, новый документ из боковой панели, учебный пример, фильтры, панель
  замечаний, устаревший разбор, импорт, отказ проверки, найденные блокеры,
  автосохранение, обучение, сурикат и журнал (включая отказ без токена). Все
  сценарии проходили на ветке `frontend/aira-ui-20261107` перед выпуском 0.2.0;
- проверка настоящей моделью на тестовом документе занимает около 13 с;
- установщики 0.1.x–0.2.1 установлены в папку с русскими буквами (подменённый
  `LOCALAPPDATA` и `/DIR`). Проверены создание базы, запуск окна через
  `AIRA_SELFTEST`, анализ моделью, закрытие и удаление через «Программы»;
- сценарий пилота воспроизведён на сборке 0.2.1: процесс убивался посреди проверки
  при `armed`. После перезапуска шли `armed → drained`, супервизор был готов за 1,6 с,
  прогон получал статус `failed/interrupted`, документы сохранялись.

## Ограничения

- Установщик с правкой из PR #47 не собирался. Путь восстановления в бэкенде
  (`_coordinator.startup_result`) и миграции между проверенной сборкой 0.2.1 и main не
  менялись, но нативная приёмка нужна со следующей сборкой Windows (после 0.2.9).
- Лицензирование, защита модели, автообновление WinSparkle, macOS и сайт скачивания
  сделал Никита. Этот документ их не описывает.
- Сборки 0.2.0 и 0.2.1 без подписи кода: SmartScreen просит «Подробнее» →
  «Выполнить в любом случае».
- Интерфейс в установленной сборке проверялся автоматически, самопроверкой и
  журналом. Ручной проход по окну делал пилотный пользователь.
- Качество замечаний модели не оценивалось. Тестовые документы с «размытыми»
  формулировками лежат в `dev/testdata/` (`model-traps-cats-meerkats.docx`, разбор в
  `model-traps-report.md`).
