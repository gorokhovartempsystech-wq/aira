# Приёмка Windows-пилота

Собрать установщик после слияния PR с пилотными логами. Зафиксировать SHA исходников командой `git rev-parse HEAD` и версию сборки в отчёте.

## Сборка

Использовать Windows, обычный Python 3.12 с tkinter, портативный PostgreSQL 18, Inno Setup 6 и распакованный пакет модели models-0.2m. Параметры путей должны указывать на подготовленные зависимости машины сборки.

Из корня репозитория:

```powershell
powershell -ExecutionPolicy Bypass -File app\frontend\packaging\windows\build.ps1 -ModelDir C:\AIRA-models\models-0.2m -PgDir C:\pgsql -Version 0.1.1
```

Если Python или Inno Setup находятся вне стандартных папок скрипта, передать также `-Python` и `-Iscc`. Выходной каталог задаёт `-Out`. Для приёмки нужен установщик с настоящей моделью. Режим `-NoModel` включает тестовый анализ.

## Прогон установленного приложения

Проверять сначала на отдельном тестовом профиле Windows. Записать версию Windows и сборки AIRA, SHA исходников и результат каждого пункта.

1. Установить и запустить с ярлыка. Дождаться редактора.
2. Создать документ, набрать требования, добавить таблицу и PNG/JPEG. Проверить отмену/повтор, редактирование ячейки.
3. Запустить проверку настоящей моделью, переключить фильтры и скрыть/вернуть замечание.
4. Запустить ещё раз, остановить, затем повторить проверку. Проверить завершение и отсутствие зависания.
5. Импортировать синтетический `app/frontend/dev/pages/sample-blockers.docx` и запустить проверку. Кнопка доступна, поддерживаемые элементы Word проходят анализ.
6. Экспортировать DOCX через системный диалог, открыть его в Microsoft Word и проверить текст, таблицу, изображение и оформление.
7. Закрыть приложение сразу после анализа. Запустить заново и открыть сохранённый документ.
8. Повторить с профилем Windows, содержащим кириллицу. Зафиксировать ошибки запуска, выбора файла или записи.
9. Скачать журнал через меню «?» → «Скачать журнал». Если интерфейс не открылся, забрать `%LOCALAPPDATA%\AIRA\logs\aira.log` и `postgres.log`.

Если проблема воспроизводится, записать время, последовательность действий, ожидаемый и фактический результат. Для передачи файла с проблемой использовать синтетический пример либо явно согласованный документ.

## Журнал пилота

Существующая локальная диагностика дополнена событиями `[ui] pilot` с фиксированным именем действия и порядковым номером. Она учитывает основные кнопки, вставку объектов, фильтры, скрытие замечаний и факт ввода в редакторе. Ввод учитывается максимум раз за пять секунд. Записи API показывают результат и `duration_ms`.

Новые события действий содержат только фиксированные имена и номер события. В журнале сохраняется прежняя диагностика ошибок. Перед передачей журнала проверить его содержимое. Журнал передаёт участник пилота вручную кнопкой скачивания. Это локальная диагностика, автоматического сбора на сервере пока нет.

Прошедший macOS backend gate содержит 7281 успешный тест и 45 пропущенных проверок, требующих Windows. Их нативный прогон остаётся отдельной платформенной приёмкой. Описанный ручной сценарий дополняет автоматические проверки.

## Текущие границы пилота

Пилотный launcher запускает приложение без серверного лицензирования. Подключение лицензии и цифровая подпись установщика остаются следующими задачами. В журнале анализа для настоящей модели должно быть `execution: local_model`.

Поддержаны согласованные обычные элементы Word. Неизвестные символы, сложные формулы, старые VML-надписи и альтернативное описание картинки могут дать явный отказ. После подтверждённого отказа должны работать экспорт, закрытие и новая проверка.
