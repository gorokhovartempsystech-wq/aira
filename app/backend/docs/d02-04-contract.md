# D02-04 — правки диапазонов текста внутри абзаца DOCX

29 октября 2026. Следующий ограниченный цикл после D02-03, часть F05/F10/F11 [текущего объёма](current-product-scope.md). Пользователь попросил продолжить разработку. Цель — редактировать выделенную фразу или вставлять текст в точке, не заставляя будущий интерфейс самостоятельно заменять целые w:t.

## Границы и API

Новые файлы только в `src/ara/docx_package/ranges/**` и `tests/docx_ranges/**`. Существующие package/projection/editing, API, БД, ML, зависимости и runner не менять. Стандартная библиотека; чистая операция над bytes, без файлов, сети, секретов, процессов, БД и логирования содержимого. Это технический слой над D02-03, без UI и структурного редактора.

`ara.docx_package.ranges` экспортирует:

```python
TextPosition(anchor: SourceAnchor, offset: int)
RangeEdit(start: TextPosition, end: TextPosition,
          expected_text: str, replacement_text: str)
RangeLimits(max_edits: int = 1000,
            max_total_replacement_chars: int = 1000000,
            max_touched_spans: int = 10000)
RangeError
export_docx_ranges(data: bytes, edits: tuple[RangeEdit, ...], *,
                   limits: DocxLimits | None = None,
                   projection_limits: ProjectionLimits | None = None,
                   range_limits: RangeLimits | None = None) -> bytes
```

SourceAnchor — существующий D02-02. Все новые DTO frozen/slotted. RangeEdit repr не содержит expected_text/replacement_text. Все поля повторно проверять при вызове, включая изменённые/удалённые обходом frozen. Коллекция строго tuple, элементы точно RangeEdit, позиции точно TextPosition, якоря точно SourceAnchor. Строки настоящие str; offset — настоящий неотрицательный int, не bool. Форма якоря как D02-03: lowercase SHA-256, непустой part_name, tuple неотрицательных int без bool. Нарушение формы — invalid_input. RangeLimits при создании и вызове проверяет настоящие положительные int; границы включительны.

Позиция задаётся локальным Unicode code-point offset внутри существующего проецируемого text span: от 0 до len(span.text) включительно. Это не UTF-16 offset и не номер байта. Явный якорь определяет сторону каретки/оформление на стыке spans; угадывание стороны по одному числу не требуется. Смещения всех edits относятся к одному исходному файлу.

## Разрешение диапазона

Заново получить авторитетную проекцию D02-02 из bytes с заданными лимитами. Обе позиции должны иметь SHA исходника, иначе stale_source, и указывать на проецируемые text spans основной части, иначе invalid_anchor. Opaque, табуляции, разрывы, properties и другие stories не являются точками редактирования.

Обе позиции должны принадлежать одному Paragraph (в том числе внутри вложенной таблицы). Offset за пределами текста, другой абзац/ячейка, обратный порядок spans или start.offset > end.offset при одном span дают invalid_range. Абсолютные позиции: span.start + offset в paragraph.text. Для равных абсолютных позиций начало и конец обязаны иметь одинаковые anchor и offset; иначе invalid_range, поскольку это неоднозначная вставка между разными, в том числе пустыми, узлами.

`expected_text` должен точно совпасть с paragraph.text[absolute_start:absolute_end], включая Unicode и пробелы; иначе text_mismatch. Для вставки это пустая строка. Для удаления replacement_text пуст. Замена диапазона равным текстом является no-op: нельзя перераспределять прежний текст между runs и тем самым менять оформление.

replacement_text содержит только разрешённые XML 1.0 символы (как D02-03), иначе invalid_input. Новые tab/CR/LF при фактической правке дают unsupported_range; их создание требует Word-элементов, которые этот цикл не добавляет. No-op сохраняет уже существующие control characters.

## Оформление и границы

При фактической правке все spans от start до end включительно должны быть text и принадлежать одной и той же гиперссылке по hyperlink.anchor (либо все иметь hyperlink=None). Даже пустые spans и граничный end с offset=0 учитываются. Иначе unsupported_range. Это предотвращает неявное превращение обычного текста в ссылку или перенос между разными ссылками. Отдельные edits внутри разных ссылок допустимы.

Замена вставляется в start span: сохраняется его prefix до start.offset, затем replacement_text. При одном span следом остаётся suffix от end.offset. При разных spans конец start span удаляется, промежуточные text spans очищаются, end span сохраняет suffix от end.offset. Runs/гиперссылки/атрибуты и пустые w:t не удаляются. Так новый текст получает оформление явно выбранного места начала, а оставшийся хвост — своё прежнее оформление. Это техническая политика будущего ручного редактора, не автофикс.

Проверить исходный main XML bounded-парсером (разрешено переиспользовать projection._parse.parse_main с теми же лимитами). D02-02 не включает bookmarkStart/bookmarkEnd в spans: при наличии WML bookmark marker, чей element-child path строго между start.anchor.path и end.anchor.path, фактическую правку отклонять unsupported_range. Foreign namespace с таким local name не блокирует. Не переносить текст через закладки молча. Маркеры вне диапазона сохраняются. No-op через такую границу допустим.

Эти ограничения на spans/hyperlinks/bookmarks применяются только к реально изменяемым ranges после проверки аргументов, адресов, текста и конфликтов. При no-op источник остаётся нетронутым. Комментарии/PI внутри изменяемого w:t, подписи, защита, tracking, поля, неподдержанные кодировки и literal tab/CR/LF в сохранённой части изменяемого w:t наследуют ограничения и безопасные ошибки D02-03.

## Несколько правок и бюджеты

Все edits сначала валидируются относительно исходника; ошибка любого не возвращает частичный экспорт. Для каждого абзаца проверять конфликты по абсолютным source offsets, включая no-op:

- Пересекающиеся непустые полуинтервалы запрещены; соседние [a,b) и [b,c) разрешены.
- Вставка конфликтует с любой другой вставкой в той же абсолютной точке и с непустым диапазоном, если её точка лежит внутри него или на любой его границе. Это относится и к разным якорям в общей позиции.
- Полностью одинаковые ranges также конфликтуют.
- Правки разных абзацев не конфликтуют; XML-порядок endpoint spans проверяется отдельно.

Конфликт даёт conflicting_edits независимо от порядка списка. Порядок любых допустимых независимых edits не влияет на итоговые bytes. Несколько правок в одном w:t объединить по исходным смещениям в **один** TextEdit. Нельзя выполнять последовательные export_docx для отдельных ranges: это сдвигает offsets и инвалидирует SHA.

RangeLimits ограничивает число входных edits и суммарную длину их replacement_text (code points, включая no-op). max_touched_spans ограничивает число уникальных w:t от start до end включительно для фактических правок; граничные/пустые узлы учитываются, no-op не учитывается. Превышение — range_limit_exceeded; проверять до создания итоговых строк/экспорта. Это технические бюджеты вызова, не продуктовый лимит документа.

После объединения сформировать только реально изменившиеся TextEdit и вызвать существующий editing.export_docx **один раз**. Для нижнего EditLimits явно задать max_edits=max(1, число сгенерированных TextEdit), max_total_replacement_chars=max(1, сумма длины их полных replacement_text). Так одна короткая правка в длинном w:t или range через 1001 span не упирается случайно в defaults D02-03. Общие DocxLimits/ProjectionLimits передавать неизменными; они по-прежнему ограничивают исходник и итоговый файл. Даже пустой batch должен проверить исходный пакет/лимиты и вернуть точные bytes.

## Ошибки и сохранность

RangeError.code: invalid_input, range_limit_exceeded, stale_source, invalid_anchor, invalid_range, text_mismatch, conflicting_edits, unsupported_range. Для каждого code постоянный непустой безопасный message, str == message, без текста/путей/XML/сырой parser chain. Ошибки существующих D02-01/D02-02/D02-03 сохраняют свои DocxError/ProjectionError/EditError; не ослаблять их проверки и не выдавать исключение за успешный пустой результат.

Все гарантии D02-03 сохраняются: точный no-op, неизменяемый исходник, лексические bytes вне изменённых w:t, остальные части/структура/стили, метаданные ZIP, валидация экспорта, новые anchors для нового SHA. После правки нужна новая проекция. Отображение Word, layout, смена стиля, переносы/табуляции, создание или удаление абзацев/таблиц и автоматические AI-правки не добавляются.

## Приёмка

Независимая приёмка родителя — `tests/acceptance/test_docx_ranges.py` и `test_docx_ranges_boundaries.py`, фиксируется красной до запуска. Исполнитель меняет только новый модуль и собственные тесты. Полный `bash scripts/check.sh` обязателен.

Проверить: substring внутри span, диапазон через несколько runs с разным оформлением, сохранение suffix, вставка/удаление/пустой w:t, Unicode offsets, несколько правок одного span/абзаца, независимость порядка, nested table и hyperlink; no-op не меняет распределение текста по runs. Отдельно stale/ошибочные/мутированные DTO, обратные диапазоны и конфликты, opaque/tab/br/revision/field, hyperlink и bookmark boundaries, лимиты, inert imports/operations и делегирование protection/output checks. Обязательно диапазон через >1000 spans и короткая правка в span длиннее 1M, чтобы доказать корректные бюджеты нижнего API.

Синтетический rich-source.docx: через новый API заменить фразу, пересекающую несколько runs, отдельно изменить substring ячейки и подписи ссылки. Сравнить нетронутые части/свойства, отрендерить bundled LibreOffice и просмотреть все страницы. Microsoft Word этим автоматически не считается проверенным. Архив пользователя не использовать. После одного цикла остановиться.
