# Проверка файлов установки

D05-03, 4 ноября 2026. `ara.desktop.installation` проверяет состав и целостность
отдельного поддерева установки. Модуль ничего не запускает и не скачивает.

Сборщик создаёт `aira-installation.json` с перечнем относительных путей, размеров,
SHA-256 и исполнительных флагов. Роли указывают Python, приложение, пять утилит
PostgreSQL, frontend entry и manifest модели. Точная схема и ограничения —
[в контракте](d05-03-contract.md). Все runtime libraries и вспомогательные файлы
также должны попасть в inventory: наличие только бинарника PostgreSQL недостаточно.

Подписанный внешний launcher или доверенный release descriptor передаёт ожидаемый
SHA-256 всего manifest. Он расположен вне проверяемого payload, что исключает цикл
«launcher содержит hash manifest, который содержит hash launcher». Hash из соседнего
недоверенного файла не подтверждает происхождение установки. OS signing и политика
защиты каталога — следующие этапы сборки.

`parse_manifest(raw, expected_sha256=..., target=...)` работает с bytes без I/O.
`verify_installation(root, expected_sha256=..., target=...)` явно читает payload
и возвращает metadata/`role_path(role)`. Оба вызова по умолчанию отвергают fixture.
Только учебный launcher передаёт `allow_fixture=True` и сохраняет явную отметку
учебного режима. Production inventory без модели не проходит проверку. При этом
валидный manifest модели в inventory ещё не доказывает её внутренний формат,
совместимость, качество или запуск: это проверяет C2 и дальнейшая интеграция.

Поддержанные имена профилей: macos-arm64,macos-x86_64,windows-x86_64. Можно проверить
Windows payload на macOS; это проверка файлов, не Windows native acceptance.
Минимальные характеристики ОС/железа и реально выпускаемые архитектуры ещё требуют
проверки пакета модели и готовой сборки.

В preflight нет исправления файлов. Отсутствующий файл даёт package_unavailable,
неверные bytes/hash — package_mismatch, лишние файлы/ссылки/неподходящая структура —
package_invalid. Сообщения фиксированы, без содержимого и локальных путей.
Чтение потоковое, до1MiB за вызов; большая модель не копируется целиком в RAM этой
проверкой. Повтор inventory обнаруживает наблюдаемые изменения во время чтения.

Это не атомарный snapshot файловой системы и не защита от владельца, способного
одновременно переписать установку. После проверки каталоги остаются обычными путями;
запускающая оболочка обязана обеспечить доверенный неизменяемый payload и выполнить
отдельные проверки запуска. DTO можно создать вручную, он не является capability.

Сборщик должен заранее заменить допустимые исходные symlinks обычными файлами
в итоговом payload, сохранить execute bits и исключить pycache/посторонние файлы.
Не менять уже подписанный bundle ради выравнивания под этот формат: формировать
собственный payload до подписи и проверять лицензионные условия его компонентов.
Mutable PG data, документы, активация и временные файлы хранятся отдельно.

Проверки используют синтетические bytes вместо настоящих executable/model/UI assets.
Отдельный native Windows gate остаётся открытым. Готового установщика, ссылки для
скачивания или подключённой модели этот модуль сам по себе не создаёт.
