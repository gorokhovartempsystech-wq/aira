# D02-08 — загрузка и сохранение DOCX через локальный HTTP

30 октября 2026. Одна ограниченная задача после D02-07, часть F05/F11/F12 текущего объёма. Пользователь выбрал прямую разработку в этом чате на Sol 6.1 High: каталог CLI model/list не содержит эту модель. Ralph не запускается, его статусы и журнал не редактируются; готовность прямой реализации фиксируется результатом общего gate в отчёте.

## HTTP-контракт

Добавить отдельный `install_docx_writes` в новом `ara.docx_documents.writes` и минимальное подключение в `app.py` после read API. Импорты инертны, зависимости и построение HTTP-схем откладываются до явной установки. Старое чтение, service/DTO, БД, лимиты пакета и ML-контракты неизменны. Без DocumentRuntime маршруты не устанавливаются; прежние server-owned user/project и local-dev контекст сохраняются.

- **POST /docx-documents/{document_id}/import?title=...** — raw bytes DOCX; ID выбирает клиент и использует для безопасного повтора. Ровно один query-ключ `title`, строка 1..200 символов, не whitespace-only, без NUL и суррогатов; сохранить точно, без trim. Передать в неизменный `import_docx`. Первый импорт и совпадающий повтор возвращают 200 с семью полями `DocxMetadata` D02-07; повтор возвращает последнюю рабочую версию без сброса правок. Несовпадающий исходник/название — прежний 409 import_conflict, чужой ID — прежний 404.
- **PUT /docx-documents/{document_id}/content?expected_storage_revision=...** — raw bytes текущего DOCX, через неизменный `save_docx`. Ровно один query-ключ ревизии: ASCII-цифры, длина 1..19, диапазон 1..9223372036854775806, ведущие нули допустимы, без знака/пробелов/дроби/exponent. Устаревшая ревизия — прежний 409 docx_conflict даже для одинаковых bytes; успешный save увеличивает ревизию и возвращает 200 DocxMetadata. Оригинал/название/created_at неизменны.

UUID — прежний HttpUUID; неправильные/повторные/неизвестные или отсутствующие query-параметры дают безопасный 422 validation_error до чтения тела и до обращения к storage. Оба успешных ответа имеют Cache-Control: no-store; bytes, original hash, owner/project и внутренние пути не возвращаются. Информация о сохранении получается из возвращённого snapshot, без повторного GET. `mark_saved` рабочей сессии вызывается клиентом только после подтверждённого сохранения; HTTP его не вызывает.

## Ограниченное чтение тела

Тело — бинарный DOCX, без multipart, JSON/base64 или временных файлов. Разрешены Content-Type application/vnd.openxmlformats-officedocument.wordprocessingml.document и application/octet-stream (регистр и внешние пробелы несущественны, параметры через `;` не разрешены). Отсутствующий/другой тип — 415 unsupported_media_type "Unsupported document media type". Content-Encoding отсутствует либо identity без учёта регистра/внешних пробелов; иной — 415 с тем же безопасным сообщением.

Повторные Content-Type/Content-Encoding/Content-Length — 422 validation_error. Если Content-Length есть, принять только ASCII-цифры длиной 1..19. Ложная длина, не совпавшая с фактически прочитанной, — 422. Пустой файл — ошибка проверки пакета 422. Content-Length и Transfer-Encoding одновременно — 422; обработку transport framing выполняет ASGI-сервер.

Лимит raw тела равен неизменному `DocxLimits().max_archive_bytes` (32 MiB). Заявленная большая длина отклоняется до чтения тела; при отсутствии длины/chunked запросе считать реально полученные bytes и остановиться при первом превышении до накопления лишнего chunk. Ошибка — 413 upload_too_large "DOCX upload exceeds a technical limit", retryable=false. Не читать всё через request.body(), не использовать UploadFile/spooling. Память приложения ограничена накопленным телом, но размер одного входящего ASGI chunk задаёт сервер. ClientDisconnect во время чтения — безопасный 422, storage не вызывается.

После ограниченного асинхронного чтения передать immutable bytes в `run_in_threadpool`: там выполняются существующая проверка DOCX/проекции, DB-транзакция и построение ответа. Event loop не блокируется ZIP/XML-проверкой или DB. DocxError и ProjectionError входящего файла становятся DocumentError 422 с их безопасными code/message; существующие DocumentError, включая corruption 500 и unavailable 503, проходят без подмены. Другие исключения не перехватывать как якобы некорректный документ. Старые глобальные обработчики не менять; не логировать тело/SQL/секреты, не открывать внешние ссылки и не читать настройки/секреты при импорте.

## OpenAPI, разрешённые изменения и приёмка

Документировать обязательный binary body для обоих допустимых MIME, обязательные query-поля, summary 200 и безопасные ошибки 404/409/413/415/422/500/503. Максимальная ревизия в OpenAPI — точное JSON integer. GET-маршруты, их параметры и прежний wrapper OpenAPI сохраняются.

Реализация: только `src/ara/docx_documents/writes.py` и две строки подключения в `src/ara/app.py`; собственные проверки при необходимости `tests/docx_documents/test_http_writes.py`. Подготовка снаружи реализации: этот контракт, новая независимая приёмка `tests/acceptance/test_docx_http_writes.py`, отчёт и ссылка из ralph-usage. Исторический test_http_boundaries заранее дополняется новым /import-адресом, исторический D02-07 factory_openapi проверяет GET+PUT для /content вместо только GET; остальные старые утверждения неизменны. Это необходимые ожидания нового API, зафиксированные до красного прогона. После фиксации новую приёмку и критерии не менять ради успеха. Runner/tasks/progress, прочие тесты/исходники, схема БД и зависимости вне границ задачи.

Приёмка: полный HTTP import→изменение DocxSession→save→новый app/engine→download, точный оригинал и текущий файл; повтор импорта и CAS, конкурентные save, изоляция/ошибки/rollback, лимит тела и early rejection, типы/encoding/обрыв, OpenAPI, импорты без I/O и выполнение storage вне event loop. Использовать только синтетические данные; архив пользователя, output/ и .artifact-build/ не читать. Проверить полный bash scripts/check.sh и сохранность локальной БД. UI, таймер, файловые диалоги, структурные правки, шаблон AIRA, анализ и полная совместимость Word остаются отдельными задачами. После D02-08 остановиться.
