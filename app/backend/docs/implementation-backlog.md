# Бэклог первого рабочего сценария

Обновлено: 18 сентября 2026. **T01, техническая T02 и T03-01 завершены**: [контракт анализа](t02-01-result.md), [сохраняемые задания/API](t02-02-result.md), [worker и fixture](t02-03-result.md), [ревизии решений](t03-01-result.md). T03-01 прошёл за одну итерацию Ralph; независимая проверка — 468 тестов и 24 подтеста. До технического сценария через API с fixture остаются два цикла: T03-02 и T03-03. До пилота — шесть крупных этапов: оставшаяся часть T03 и T04–T08. Выбор ML-провайдера и доступ к Confluence не мешают завершению локальной T03. Runner проверяет одну выбранную задачу и не продолжает бэклог автоматически.

Основание: [рабочая спецификация](<./docs/mvp-implementation-spec.md>) и [контракт ML](<./contracts/README.md>).

Предлагаемое распределение по известному контексту: Никита — backend; Артём — ML; Анна — проверка сценариев и разметка. Исполнитель frontend ещё не определён. Это предложение работ, не отправленные людям поручения.

## T01. Каркас и сохранение документа

**Статус:** завершено для локального технического режима. Реализованы T01-01…T01-04; настоящий вход относится к T06, Merge/apply — к T03. Новые версии пока создаются через Python-слой хранения.

**Ответственность:** backend. **Зависимости:** нет зависимостей от ML/Confluence. **Результат:** создать документ и прочитать его после перезапуска.

Сделать приложение FastAPI с PostgreSQL, конфигурацию, миграции User/Project/Document/DocumentVersion и разбиение Markdown на блоки. Версии Python и библиотек зафиксировать в окружении/lock-файле при реализации. Добавить локальный режим тестового пользователя, запрет его использования в пилотной конфигурации и подмену аутентифицированного пользователя в тестах. Реализовать GET /me, POST /documents, GET /documents и чтение версии. Все секреты загружать из ~/secrets.env.

**Готово, когда:** документ с заголовком, таблицей и блоком кода возвращается без потери содержимого; предыдущая версия не меняется при создании следующей; другой тестовый пользователь не читает документ; миграции проходят на пустой БД; README содержит проверенную команду запуска и проверки.

**Границы задачи:** работа с документом и данными; модель и фоновые задания входят в T02.

## T02. Контракт и сохраняемое задание со stub-адаптером

**Статус:** завершено в техническом режиме fixture. T02-01…T02-03 реализуют модели 0.1.0, валидатор, JSON Schema/OpenAPI, сохраняемые задания, идемпотентность, worker с lease/attempt/deadline и ограниченными повторами. Валидированный результат доступен по HTTP; needs_clarification остаётся succeeded. Реальный смысловой анализ и качество ML относятся к T04/T05.

**Ответственность:** backend, сверка интерфейса с ML. **Зависимость:** T01. **Результат:** API принимает Linting/Merge и возвращает сохранённый тестовый результат с явным execution_mode=fixture.

Реализовать типизированные модели контракта 0.1.0, проверку ссылок, цитат, покрытия и зависимостей. Из моделей сгенерировать схемы, а HTTP API описать через OpenAPI. Создавать ContextRevision и AnalysisRun, отдельным worker выполнять воспроизводимый сценарий; сначала использовать [JSON-примеры](<./contracts/examples/merge-result.json>). Сделать lease, attempt ID, ограниченные повторы и idempotency при создании задания. Stub формирует ссылки и ID для конкретного входа; сохранённый пример не выдаётся без адаптации за анализ произвольного документа.

**Готово, когда:** запрос получает run_id, проходит queued/running/succeeded и доступен после перезапуска; needs_clarification остаётся успешным смысловым результатом; отсутствующая цитата/ID, циклическая зависимость и фиктивное покрытие отклоняются; падение worker позволяет повтор без двух итоговых результатов; завершение устаревшей попытки не перезаписывает новую; чужой пользователь не читает задание.

## T03. Решения, preview и новая версия

Три последовательных цикла: **T03-01 завершён** — неизменяемые ревизии решений и текстовые правки предложений ([контракт](t03-01-contract.md), [результат](t03-01-result.md)); **T03-02** — preview, diff и проверка применимости; **T03-03** — атомарное применение в новую версию. Критерии и независимые проверки следующих циклов фиксируются перед их отдельным запуском.

В T03-01 доступны GET/PUT `/runs/{run_id}/review`: виртуальная ревизия 0 без записи, полный снимок `pending`/`accepted`/`rejected`/`deferred`, точные текстовые edits, история и проверка ожидаемого родителя/fingerprint при сохранении. Оба метода возвращают ReviewResponse из 11 полей. Принятие группы — намерение пользователя; вопросы, непринятые зависимости и альтернативы допускаются в черновике. Исходный результат и документ не меняются; preview/apply ещё нет.

**Ответственность:** backend. **Зависимость:** T02. **Результат:** выбрать правки из результата и получить новую версию документа.

Осталось реализовать preview полного документа и diff, затем применение выбранных групп со всеми зависимостями и проверкой вопросов, конфликтов и unsupported-блоков. Применение должно быть транзакционным и повторяемым по ключу запроса; новая версия должна сохранять связь с результатом и ревизией решений.

**T03 целиком готова, когда:** в примере Merge можно применить g1; применение g2 заблокировано q1, а исходный запрос остаётся частично решённым; отклонённый текст не попадает в новую версию; незатронутые блоки сохраняются; повтор возвращает ту же созданную версию; конкурирующая правка даёт конфликт устаревшей базы; изменение решения после preview делает старый preview неприменимым.

**Демонстрация:** создать документ → запустить stub → увидеть вопросы → принять g1 → просмотреть итог → сохранить → перезапустить → прочитать обе версии. Это первый законченный технический результат.

## T04. Реальный Linting и оценка полезности

**Ответственность:** ML, backend-адаптер; разметка с аналитиком/QA. **Зависимость:** T02. **До подключения:** выбрать доступный провайдер/модель и допустимые данные. Реальные документы не отправляются новому внешнему провайдеру в рамках работы над заглушкой.

Подключить выбранный ML через тот же контракт. Разметить L01/L02 и примеры без ошибок, неоднозначностей и неполного содержимого. Обрабатывать невалидный ответ, timeout, ограничение объёма и провайдерскую ошибку. Версии модели/промпта, попытки и фактические затраты фиксирует worker.

**Готово, когда:** показана работа на независимых от настройки примерах; составлен отчёт по корректным/ложным замечаниям, пропускам и ссылкам; нет подмены потреблённых ресурсов выдуманными значениями; согласованные перед приёмкой критерии качества выполнены. Пока критерии не определены, задачу нельзя закрыть только из-за HTTP 200.

## T05. Реальный Merge и цикл уточнений

**Ответственность:** ML + backend. **Зависимости:** T03 и работающий ML-адаптер T04.

Реализовать выбор мест изменения, группы, вопросы и судьбу каждого входного требования. Ответы пользователя создают новую ContextRevision и новый запуск. Отдельно проверить M01B: система учитывает бизнес-контекст классификации, не объявляет Z1 реле и не считает выбранную пользователем иконку аппаратным фактом.

**Готово, когда:** на размеченном кейсе возвращаются обоснованные правки и необходимые вопросы; ответ на вопрос связан с новым результатом, а старый сохраняется; результат не придумывает возможности адаптера; критерии приёмки меняются согласованно с требованиями; незатронутый смысл сохраняется; показатели качества сопоставлены с заранее согласованной разметкой.

## T06. Вход и интерфейс первого прохождения

**Ответственность:** backend + исполнитель frontend, QA. **Зависимости:** интерфейс можно начинать после T02, сохранение требует T03. **Перед пилотом:** выбрать один механизм входа и инфраструктуру его работы.

Реализовать реальный вход/выход и истечение сессии, личные документы, рабочий экран с замечаниями/группами/вопросами, ответы на уточнения, preview и историю версий. При первом входе предложить учебный пример. Figma/Lovable используются как ориентир; бизнес-поведение задаётся спецификацией и контрактом.

**Готово, когда:** новый пользователь проходит сценарий; заглушка, вопросы, неполная проверка и техническая ошибка визуально различимы; два реальных пользователя изолированы; выход/повторный вход не теряет работу; dev-auth выключен в пилоте.

## T07a. Проверка доступа к Confluence DC

**Ответственность:** backend + владелец тестового сервера. **Зависимость:** известны тестовый сервер и разрешённый доступ; от ML не зависит.

Определить версию Data Center, сетевую доступность из будущего окружения и способ авторизации. Прочитать одну разрешённую страницу, её версию и структуру; проверить отсутствие доступа к другой закрытой странице.

**Готово, когда:** есть воспроизводимый результат чтения или конкретный внешний блокер с указанием требуемого действия. Ошибка сети/прав не считается завершённой интеграцией. Секреты не попадают в документ проверки.

## T07b. Импорт страницы

**Ответственность:** backend + frontend. **Зависимости:** T01, T07a; настоящий пользователь до пилота — T06.

Подключение по владельцу, выбор страницы, импорт поддержанных структур и отчёт о пропусках. Хранить page ID и внешнюю версию. Обновление создаёт новый снимок, не перезаписывает локальные правки. Ссылки на страницу проверять в рамках зарегистрированного подключения; секреты не отправлять модели.

**Готово, когда:** импортируются текст, заголовки и выбранные поддержанные таблицы; макросы/изображения с неподдержанной обработкой явно отмечены; ошибки сети, прав и истёкшего доступа объяснимы; новая внешняя версия видна; пользователь не получает чужой импорт. В этом этапе обратной записи нет.

## T08. Проверка пилота

**Ответственность:** вся команда, приёмка — аналитик/QA. **Зависимости:** T04–T07b.

Пройти сценарии настоящего пользователя, проверить восстановление после сбоев, гонки версий, отсутствие тихой потери содержимого и полезность замечаний. Установить измеренные ограничения объёма/времени/стоимости, проверить наблюдаемость ошибок и политику хранения/удаления данных пилота.

**Готово, когда:** результаты проверок приложены, ограничения видны пользователю, критичные проблемы устранены, качество ML соответствует согласованной оценке и основной сценарий воспроизводится на тестовом DC. Демо со stub не засчитывается за готовность T08.

## Выполнение короткими циклами

На один цикл брать одну задачу или её ограниченный фрагмент: прочитать актуальную спецификацию → реализовать → проверить критерии поведения → просмотреть diff → записать результат и оставшиеся ограничения. Если задача не помещается в один проверяемый результат, разделить её, сохранив зависимости. Автоматическая серия циклов не должна переписывать scope или ослаблять критерии ради зелёного статуса.

Для T01 команда проверки появляется после создания окружения; её нужно проверить и записать в README. В последующих задачах использовать эту команду и добавлять проверки новых рисков. Финальный статус задачи подтверждается файлами реализации и результатом выполнения, не одним заявлением агента. Изменения исходного архива в задачи реализации не входят.
