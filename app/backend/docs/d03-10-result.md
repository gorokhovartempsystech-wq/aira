# D03-10 — создание нового документа в приложении

30 октября 2026. Реализован [контракт D03-10](d03-10-contract.md), часть F04/F05/F11/F12 [текущего объёма](current-product-scope.md). Пользователь задаёт название, создаёт пустой DOCX по шаблону AIRA, сразу вводит первый фрагмент, сохраняет, скачивает и повторно открывает документ. Это расширение текущего локального workspace, не desktop-установщик или структурный редактор.

## Поведение

Добавлен один маршрут `POST /docx-documents/{document_id}/create?title=...` только с явным local runtime. Тело отсутствует: сервер генерирует неизменный blank D03-09 и передаёт его прежнему import_docx. Генерация и storage выполняются в worker thread. Metadata и no-store прежние, OpenAPI описывает маршрут без requestBody. Default factory остаётся health-only.

UUID клиента — ключ повтора. Первое создание и повтор возвращают HTTP 200; повтор после редактирования возвращает последний current DOCX, не сбрасывает его к пустому исходнику. Параллельные повторы создают одну строку. Другое название/исходник на том же ID даёт creation_conflict 409, чужой scope — 404. Новый origin-флаг не добавлялся: импортированный побайтово такой же blank с тем же ID/title эквивалентен повтору. Будущее изменение bytes шаблона может потребовать отдельного решения для старого replay; консервативный конфликт не переписывает исходник.

Проверяются единственный title, strict UTF-8/percent escapes, UUID, заголовки и пустой stream. Непустой chunk или disconnect останавливает обработку до генерации/БД; накопления body нет. Ошибки генерации безопасно отображаются как creation_error 500, прежние storage 500/503 сохраняются. Новых секретов, авторизации, миграций, зависимостей или моделей БД нет.

Отдельная форма «Новый документ» хранит RAM attempt UUID/title до подтверждения. Название блокируется на время неясного результата, повтор использует тот же ключ. Подтверждение с чужим UUID не очищает attempt. Перед POST подтверждается recovery copy активного текста и проверяется лимит вкладок. Ошибка оставляет текст в прежней вкладке. Повтор для уже открытого UUID сохраняет его RAM draft/history, после подтверждения неудача списка/view не предлагает повторное создание.

Blank при успешном просмотре открывает пустой фрагмент для ввода; восстановленный draft имеет приоритет. Beforeunload учитывает неясную попытку создания. «Завершить попытку» требует диалог: завершение убирает только локальный ключ и не удаляет возможный созданный документ. Импорт использует отдельный attempt; его прежнее поведение сохранено. Форма адаптирована к узкому экрану и использует обычные labels/buttons без inline script/style.

## Проверки

Коммит подготовки **a8f1c3a** заморозил контракт и **33 acceptance cases**. По прямому разрешению Никиты «Да, добавить новую строку в тест» добавлена ровно строка `/docx-documents/{document_id}/create` в старый точный список API tests/documents/test_http_boundaries.py; все прежние строки и assertions сохранены. После подготовки acceptance и старые тесты не менялись.

Красный прогон до реализации: **31 failed, 2 passed**, 3 предупреждения, **4,50 секунды**. Уже существующий 404 для отсутствующего маршрута объясняет две зелёные scope-проверки. После реализации новый acceptance вместе с прежним test_http_boundaries: **40 passed**, 4 предупреждения, **4,41 секунды**.

Дополнительно девять собственных проверок: malformed URI без replacement, остановка stream на первом непустом chunk/disconnect, выполнение генератора/storage вне event loop, literal title и сохранение retryable/error envelope. Итог **9 passed**, 2 предупреждения, **0,90 секунды**. В тестовой заглушке 503 уточнён её retryable-флаг, как у настоящей ошибки хранилища; assertions сохранены. Эти новые дополнительные тесты не были частью замороженной приёмки.

Первый общий gate остановился на Ruff из-за длинной строки в новом дополнительном тесте; форматирование исправлено. Полный повтор `bash scripts/check.sh`: **1576 passed, 24 subtests**, 69 предупреждений, **309,50 секунды**, exit 0. Ruff/format проходят. Логи `.runtime/d03-10-red.log`, `d03-10-targeted.log`, `d03-10-boundaries.log`, `d03-10-full-check.log`, `d03-10-final-check.log`. Проверки не ослаблялись, предупреждения не подавлялись. ## Браузер и DOCX

В собственной disposable БД через UI созданы четыре synthetic документа A/B/C/D. Для A сразу открылось пустое поле, первая ручная правка записала `Устройство сохраняет свой тип после переименования.` на ревизии 2. Название осталось metadata, в файл не подставилось.

Затем при dirty A создан B, middleware потерял ACK после успешного commit. A осталась с прежним текстом и историей. «Остаться» в диалоге завершения сохранило ключ; обновление списка показало существующую B. B открыта из списка, в неё введён черновик; «Повторить создание» с тем же UUID подтвердило исходную строку и сохранило текущий draft B. В списке осталось два документа, B — ревизия 1. Контроль `replayed.json`, журнал requests.jsonl: для B один path с returned_status 503, затем 200.

При отказе recovery copy попытка создать C не отправила POST, число create-запросов осталось три; B и её текст остались на экране. После восстановления копии тот же retry создал C. Одновременно проверены отказы view/list: создание подтвердилось, attempt очистился, download доступен. «Обновить документ»/«Обновить» восстановили просмотр и список без нового create.

Для D снова потерян ACK; явное «Завершить попытку» сняло retry-key, а документ остался в списке. Возврат к A сохранил её черновик и Undo/Redo; Undo к записанному тексту и закрытие clean-редактора удалили только recovery copy A. A закрыта и повторно открыта из списка с записанным текстом. После закрытия всех вкладок и reload ни одна не открылась автоматически; явный open B восстановил её текст `Черновик B не сбрасывается повтором создания.` из recovery copy.

Итог QA: A2/B1/C1/D1, четыре строки документов, один receipt правки A, одна recovery copy B. Журнал содержит пять POST создания для четырёх UUID, включая повтор B; новых запросов для ошибки копии нет. Снимки/журнал в `.runtime/d03-10-qa`.
