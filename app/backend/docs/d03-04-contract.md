# D03-04 — повтор сохранения после потери ответа

30 октября 2026. Одна задача после D03-03: явное сохранение одного DOCX span с устойчивым идентификатором попытки. Основание — F05/F11/F12 текущего объёма. Прямая разработка здесь на Sol 6.1 High по ранее выбранному пользователем режиму. Без runner/tasks/progress, нового endpoint, автосохранения и восстановления после закрытия приложения.

## HTTP и транзакция

Прежний POST text-edit получает необязательный `Idempotency-Key`: ровно один canonical lowercase UUID (`str(UUID(value)) == value`), без trim/coercion. Неверный/дублированный ключ — 422 validation_error до чтения тела/БД. Без ключа D03-03 остаётся неизменным, включая строгий CAS и старый конфликт при повторе. JSON, лимиты, threadpool, wire receipt из семи полей со строковой ревизией и безопасные ошибки сохраняются. Заголовок документируется в OpenAPI.

С ключом проверяется scope, затем под FOR UPDATE блокируется docx_documents; этот lock общий с прежними writers. Проверить целостность original/current. По паре (document_id, operation_id) найти receipt. Отпечаток запроса — SHA256 UTF8 JSON от четырёх валидированных полей, sort_keys=True, ensure_ascii=True, separators=(',', ':'); порядок ключей, пробелы и JSON escaping не влияют, значения текста/anchor/revision влияют. Текст запроса в ledger не хранить.

Совпавшие ключ+отпечаток возвращают **исходные метаданные операции**, даже после более поздней записи; никаких повторных экспорта/записи/ревизии. Тот же ключ с другим запросом — 409 idempotency_conflict, `Edit attempt does not match`. Новый ключ требует исходную ожидаемую ревизию, точный anchor/expected text и неизменный export_docx; ограничения protected/signed/tracked не обходить. Обновление current bytes/hash/revision/time и вставка receipt совершаются одной транзакцией. Receipt готовится до commit, ответ возвращается после commit. Ошибка экспорта/flush/commit откатывает оба изменения. Если commit состоялся, но подтверждение потерялось, ответ 503 допускает повтор того же запроса/ключа, который получает сохранённый receipt. Операция не определяется по совпадению текста или bytes.

Ledger: новая миграция 0007_docx_edit_receipts после 0006 и ORM DocxEditReceipt. Таблица docx_edit_receipts, десять NOT NULL колонок: document_id UUID FK docx_documents.id без cascade, operation_id UUID, request_sha256 TEXT hex64, title TEXT длиной 1..200, storage_revision BIGINT >1, current_sha256 TEXT hex64, current_size_bytes BIGINT >0, document_created_at/document_updated_at TIMESTAMPTZ без default, created_at TIMESTAMPTZ clock_timestamp(). PK(document_id,operation_id), все constraints именованные, дополнительных indexes нет. Не хранить plaintext запроса или DOCX. При повторе валидировать metadata/отпечатки, receipt revision не выше current; при равной ревизии сверять metadata с current, иначе безопасный 500. Результат не зависит от памяти процесса. Очистку ledger пока не добавлять: удаление receipt лишило бы поздние повторы гарантии.

## UI

При первом сохранении сформировать UUID и неизменный сериализованный payload. При сетевой ошибке/тайм-ауте/5xx/некорректном ответе удерживать эту пару и текст в памяти; поле доступно для выделения/копирования, но readOnly. Кнопка «Повторить сохранение» отправляет ту же пару. Показать, что результат ещё не подтверждён. После подтверждённого 200 закрыть draft и обновить view как прежде; ошибка последующего GET не отменяет подтверждение. Окончательный 4xx оставляет текст и разрешает исправлять его с новой попыткой, без принудительной записи. Старый конфликт сохраняется при конкурирующем изменении. Выбор/отмена с неподтверждённой попыткой требует существующего явного discard-dialog и предупреждает, что запись могла состояться; отмена не обещает откат. beforeunload/dirty download guard остаются. Новых browser storage, зависимостей, таймеров и автоматического повтора нет.

Миграция upgrade/repeat/downgrade сохраняет все старые строки/схемы и точные bytes; constraints и ORM совпадают. Общий bash scripts/check.sh. В браузере — искусственно потерять ответ **после** реальной записи, увидеть удержанный текст и повтор, подтвердить одну ревизию/один receipt, затем новую правку/скачивание и конкурентный конфликт. QA только synthetic/собственная временная БД. Основную БД мигрировать только после зелёных проверок с проверкой сохранности прежних данных по метаданным/счётчикам. После D03-04 остановиться.
