# Лицензирование AIRA — технический проект

## Защита локальной модели — MP01–MP04, 13 ноября 2026

Основание — запрос Никиты в чате внедрить умеренную защиту весов и его согласие
однократно повторить активацию после обновления. Последующие запуски автоматические.
Это дополнение проектирует новую цепочку; существующий протокол запуска v1 не меняется.
Реализованы контейнер, серверный proof владения ключом устройства, native credential
vault, защищённый приватный канал worker и требования к упаковке. Точный контракт,
границы защиты и поставки — в [model-protection-protocol.md](model-protection-protocol.md).
Старые установщики и ранее распространённые веса остаются доступными в прежнем виде.
Готовность конкретного опубликованного релиза подтверждается отдельно его проверками.

Цель — усложнить извлечение готового ONNX из установщика и запуск без действующей
лицензии. Пользователь с контролем над процессом может перехватить ключ или веса;
клиентская проверка устройства не является аппаратной аттестацией. Шифрование не
защищает Python-правила прототипа и само по себе не предотвращает изменение клиента.

### Контейнер модели

`ara.model_protection` шифрует один самодостаточный ONNX: magic `AIRA-MODEL` +
нулевой байт + версия 1, uint32 big-endian длина заголовка, канонический ASCII JSON
`model_id/version/size`, случайный 96-bit nonce и AES-256-GCM ciphertext/tag.
Весь префикс с заголовком — AAD. Порядок JSON ключей лексикографический, пробелов нет,
лишние/повторные поля и альтернативное кодирование запрещены. ID/version ограничены
96 ASCII символами, заголовок — 1024 bytes, модель — 512 MiB. Это технический предел
формата, не пользовательский предел размера документа. Зависимость cryptography
зафиксирована в requirements.lock. Собственные криптографические алгоритмы не пишем.

Ожидаемые model_id/version задаёт доверенная конфигурация загрузчика, не контейнер.
Расшифровка возвращает bytes только после проверки тега и всех размеров. Функции не
читают окружение, сеть или файлы и не создают открытых временных ONNX. Гарантии
обнуления Python/ONNX памяти, отсутствия копий в swap и crash dumps нет. Защита
моделей с external-data требует отдельной поддержки; обход через открытый файл запрещён.

Ключ релиза случайный 256-bit, отдельный от лицензионного ключа. Он передаётся
библиотеке явно. Для реальной упаковки/сервера секреты загружаются при явном запуске
из ~/secrets.env, не при импорте. Ключей в коде, манифесте, аргументах процессов,
логах или Git быть не должно. Тесты используют только синтетические bytes и
случайные одноразовые ключи в памяти.

### Состав реализованных циклов

1. MP02 — серверная регистрация публичного ключа устройства после предъявления
   лицензионного ключа; challenge/proof владения закрытым ключом при выдаче доступа
   к конкретному релизу. Старого license_id/device digest недостаточно. Challenge
   одноразовый, ограничен серверным сроком и атомарно потребляется в PostgreSQL;
   ответ привязан к текущему запросу, устройству, версии и digest пакета. Повторная
   проверка enabled/expiry обязательна в той же операции. Старые endpoints не
   начинают выдавать ключ модели. Требуются версионированный контракт и миграция.
2. MP03 — интеграция клиента, штатное хранилище учётных данных macOS/Windows,
   однократная повторная активация старых установок, загрузка ONNX из bytes и
   передача разрешения в изолированный worker через управляемый приватный канал.
   Нельзя добавлять секреты в argv, stderr/stdout или общий environment. Перенос
   секрета через существующий протокол worker требует отдельной проверки владения
   FD/HANDLE и закрытия при отмене/ошибках на каждой ОС. Интернет остаётся обязателен
   при запуске; дополнительная онлайн-проверка каждого анализа не вводится молча.
3. MP04 — упаковка защищённых релизов и сквозная проверка macOS/Windows. Защищённая
   сборка не содержит открытых весов и не откатывается к ним при отказе сервера.
   Документы остаются локальными; сбой защиты не удаляет их и не блокирует экспорт
   уже внесённых изменений. Ключ релиза отсутствует в установщике и updater feed.

Приёмка включает: неверный ключ, подмену любого байта, обрезку/дописанные данные,
смену модели/версии, недействительную/чужую лицензию, повтор challenge, отзыв/истечение,
обрыв сети, закрытие приватного канала и сохранность документа. Проверка ключа и
пакета не заменяет проверку native-сборок. Смена ключа нового релиза не отзывает
ранее полученные веса; ключи прошлых версий нельзя считать восстановленной тайной.

Ниже сохранён прежний проект лицензирования v1; его реализованные ограничения
и протокол не объявляются изменёнными этим дополнением.

серверной таблице от первой активации, одно устройство, онлайн-проверка при каждом

## Последовательные циклы

1. D04-01: pure правила срока/устройства, строгий протокол и привязка ответа к
   текущей попытке запуска/времени. Без HTTP/SQL/OS/disk side effects.
2. D04-02: отдельное серверное PostgreSQL-хранилище, атомарная активация/check,
   ограниченный HTTP API и ручная выдача через доверенного оператора.
3. D04-03: клиент HTTPS, определение устройства, сохранение идентичности активации,
   управление запуском/ошибками. Desktop wiring — в последующем цикле поставки.

Это три цикла из прежней оценки3–5, не новые функции. Каждый получает собственный
контракт/acceptance/red/full/result/локальный commit. Граница D04-02/03 уточняется
до freeze; библиотека сама по себе не означает защиты всего приложения.

## Данные и доверие

Сервер получает ключ при активации либо UUID лицензии при check, versioned digest
устройства и случайный256-bit nonce текущей попытки. Документы/результаты/имя
пользователя не отправляются. Ключ не сохраняется на клиенте и не логируется.
Сервер хранит HMAC-SHA256 ключа с явно переданным pepper, операционный pepper
только из ~/secrets.env. Тестовые случайные значения существуют только в памяти.

На диске клиента — публичный UUID лицензии и digest устройства, не разрешение
офлайн-запуска. Device-v1: domain-separated hash платформы и стабильного platform
UUID. Raw hardware UUID не отправляется и не сохраняется. Native readers и
стабильность ещё проверяются в D04-03. Это привязка штатного клиента, не аппаратная
аттестация и не защита от изменения его кода. Копия activation state на другой
машине не проходит check с заново вычисленным device digest.

Каждый запуск/retry генерирует новый nonce. Ответ принимается из текущего HTTPS
к заданному серверу с проверкой сертификата/имени узла. Редиректы, отключение TLS
verification и HTTP fallback запрещены. Nonce/operation/device и при check UUID
лицензии совпадают. Разрешение не загружается с диска и не сохраняется для нового
запуска. Для выбранного online-only режима отдельная подписанная офлайн-лицензия
не нужна: подлинность обеспечивает проверенный TLS, nonce связывает попытку.
Pure decoder не доказывает подлинность произвольных входных bytes.

Основания: [Python TLS](https://docs.python.org/3.12/library/ssl.html#ssl.create_default_context),
[HTTPX](https://www.python-httpx.org/advanced/ssl/),
[OWASP HTTPS](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#https).
Транспорт/конечные тайм-ауты/admission проверяются отдельно от pure D04-01.

## Время, повторы и сохранность

duration_seconds — положительное целое без фиксированного тарифа; timestamps —
UTC epoch milliseconds. Первая активация под блокировкой строки фиксирует
device/начало/конец. Повтор тем же устройством сохраняет эти поля; другому отказ.
Check не активирует. now_ms>=expires_at_ms означает истечение. Частично заполненная
запись считается повреждённой, не новой. enabled=false запрещает следующий
запуск/активацию; мгновенный отзыв текущего сеанса не обещается. Продление, перенос,
аккаунты/платежи и админский веб-интерфейс не добавляются этим проектом.

Клиент рассчитывает остаток от серверного checked_at_ms на непрерывных часах,
включающих сон. Дедлайн отсчитывается от начала запроса: сетевой интервал списан
консервативно, ещё1ms снята за округление server clock. Ответ старше15s отвергается.
Это предел попытки, не длительность лицензии. В уже разрешённом запуске сеть
повторно не требуется; локальный дедлайн закрывает новые защищённые действия.
Каждый новый запуск опять требует сервер. Истечение/ошибка не удаляют документы;
сохранение уже введённого текста и выгрузка остаются доступны при будущем desktop
wiring. Это техническая защита сохранности F11/F12, не бесплатное продление доступа.

Потеря ответа после COMMIT разрешается повтором того же ключа/устройства; срок
остаётся первоначальным. Ответ новой попытки может иметь другой checked_at/nonce.
Бесконечная история nonce серверу не нужна; повтор не увеличивает entitlement.

## Поставка

БД лицензий отдельна от локальных документов/migrations; main V8 не мигрировать.
Импорт модулей/DTO не читает секреты/clock/файлы и не открывает сеть/БД. Серверный
домен/TLS/хостинг не считаются готовыми; ничего не публикуется. До клиентского и
desktop wiring прежнее development app не объявляется лицензированным.
