## 1. Решение вопроса pre-return

Сохраняем JOB_LIST при creation, два неназванных Job и единственных владельцев их HANDLE. Не вводим create→Assign, брокер, службу, дополнительного владельца Job или PID cleanup. Microsoft рекомендует JOB_LIST для устранения пользовательского промежутка между созданием suspended process и его назначением в Job. Это основание выбора API; оно **не является наблюдением завершения конкретного процесса**. [Microsoft: creation in a Job](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812).

Разделяем платформенное ожидание containment и доказательства runtime. Смерть caller внутри CreateProcessW больше не описывается как безусловно подтверждённая физическая очистка. Если вызов не вернулся живому владельцу, E3 не создаёт fictitious PROCESS_INFORMATION, exit code или cleanup ACK. Не найдено нового первичного основания для более сильной гарантии; отсутствие такого основания также не доказывает баг Windows. Стресс-тест не доказывает все внутренние interleavings ядра.

| Наблюдаемый исход create | Что разрешено |
|---|---|
| Native call ещё не начат | Отказ/Stop, закрытие собственных ресурсов; child не создавался |
| Native BOOL=FALSE штатно получен | Failed creation по контракту API; output PROCESS_INFORMATION не использовать. Проверить свой Job и I/O, закрыть свои handles; никогда не повторять create в этой попытке |
| Native BOOL=TRUE, валидные process/thread HANDLE сохранены | Проверить membership; Resume максимум один раз. На ошибке teardown по этим retained handles/своему Job, затем actual wait |
| BOOL=TRUE, output неполон/недостоверен, либо исход вызова утрачен из-за исключения | `creation=unknown`, H, никакого Resume/GO; после выхода из native call запросить teardown собственного Job, удерживать quarantine; пустой Job не доказывает отсутствие неизвестного child |
| Caller умер до возврата/фиксации результата | Нет живого E3 record, способного подтвердить результат. У выжившего S при смерти G — H и teardown outer Job; потерянный M proof не восстанавливать. Новый S не получает прежние capabilities из PID/чисел HANDLE |

Штатный FALSE и неизвестный исход принципиально различаются: не превращать каждую обычную ошибку запуска в вечную неизвестность, но и не выдавать исключение wrapper за FALSE. CreateProcess возвращает BOOL и выходные handles; `ResumeThread` возвращает прежний suspend count. Значение1 — единственный допустимый успех resume;0, >1, 0xffffffff или исключение — H, без повторного resume. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [ResumeThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread).

**Stop во время native create не закрывает Job/attribute buffers из другого потока.** Ставится latch/event; при возврате сначала clock/Stop, потом решение о resume. Если вызов не вернулся, максимум один launch thread и один strongly retained record остаются занятыми; нет timeout→забыть thread→новый spawn. Нельзя обещать bounded CreateProcessW или прервать его безопасным CloseHandle. Зависший ещё suspended/bootstrap child не получает GO/request. Аварийная смерть процесса остаётся отдельным unknown cut point.

## 2. Recovery boundary и три разных подтверждения

E3 не освобождает caller-owned SlotLease и не пишет SQL. `resources_closed`, физическое завершение известного G/его Job, trustworthy M closed status и итог SQL — разные факты. Ни один из них не устанавливается по одному успешному Terminate/Close/CancelIoEx. Нет успешного анализа без всей композиции E4/C1B.

При живом S и unknown creation record/slot сохраняются, admission закрыт; повторные calls только опрашивают сохранившееся evidence и завершают своё I/O. Истечение SQL lease/reaper может завершить run в БД, но **не снимает локальный quarantine**. При недоступной БД источник/прежний result сохраняются, нет новой модели и публикации. E3 не вызывает `acknowledge_cancel` и не генерирует новое бизнес-состояние SQL.

После смерти S прежний RAM record потерян. C1F не имеет права автоматически снять неизвестность по свободному analysis.slot, terminal SQL или отсутствию running rows: reaper мог уже изменить статус, а новый процесс не знает о прерванном create. E3 **не реализует автоматический restart recovery для этой ветки**. Windows production admission после потери владельца остаётся закрытым до отдельного C1F restart-контракта и его тестов. Новому экземпляру fixture factory также нельзя приписывать восстановление предыдущего процесса: она используется в изолированном тестовом lifecycle, не в startup приложения.

Точное обязательство C1F перед подключением Windows: durable crash fence, установленный **до любого create** и снимаемый лишь после physical proof + SQL reconciliation + I/O quiescence, либо другое явно обоснованное независимое доказательство, покрывающее то же окно. Нужна запись вне стираемого reaper состояния; существующие run/attempt statuses не являются таким доказательством. Формат/атомарность fence и подтверждение нового OS boot проектируются в C1F до изменения БД/файлов. Простое сообщение пользователя «перезапустил», wall clock или новый GetTickCount64 origin не снимают fence. E3 не добавляет молча migration/служебный файл и не закрывает этот gate. При неопределённости безопасный исход — анализ недоступен, документы доступны по прежним функциям.

Таким образом, E3 можно реализовать без недоказанного обещания automatic crash cleanup. Это не уменьшает полную приёмку C1E/C1F: restart gate явно остаётся незавершённым, как и native Windows gate. В оценку не добавляется новый цикл: recovery уже входит в C1F.

## 3. Разрешённые изменения и ABI

Новые файлы `src/ara/docx_analysis_worker/windows/{_process_abi,_jobs,_spawn,_adopt,_launch,_bootstrap,_guardian,_guardian_entry,_child_bootstrap,_child_entry,_fixture_child}.py`. Новая frozen acceptance `tests/acceptance/test_docx_analysis_windows_guardian.py`, собственные `tests/docx_documents/test_analysis_windows_guardian_*.py`. Этот контракт и новая acceptance фиксируются до source; result/status docs после gates. Root exports, E1/E2/macOS source, старые tests, wire, DDL, dependencies, scripts/check.sh, runner/tasks/progress не менять. Если exact API требует изменения E2 — отдельный явный конфликт, не обход проверки thread ownership.

`_process_abi.ProcessAPI` — lazy composition поверх Native/IO, без изменения их исходников. Standard ctypes, все signatures фиксированы. Дополнительные bindings: CreateJobObjectW, Set/QueryInformationJobObject, IsProcessInJob, TerminateJobObject, Initialize/Update/DeleteProcThreadAttributeList, CreateProcessW, ResumeThread, WaitForSingleObject/WaitForMultipleObjects, GetExitCodeProcess, TerminateProcess, SetHandleInformation, GetWindowsDirectoryW, GetNamedPipeInfo. DuplicateHandle для reduced rights вызывается с явным desired_access, options=0; SAME_ACCESS не используется для event у G. No OpenProcess/OpenThread/OpenJobObject/AssignProcessToJobObject.

Win64 layouts обязательны: STARTUPINFOW104, STARTUPINFOEXW112 (attribute pointer offset104), PROCESS_INFORMATION24 (process0/thread8/PID16/TID20), BASIC_LIMIT_INFORMATION64, IO_COUNTERS48, EXTENDED_LIMIT_INFORMATION144, BASIC_ACCOUNTING_INFORMATION48 (ActiveProcesses40). Windows DWORD/BOOL32, SIZE_T/ULONG_PTR/HANDLE64; wchar buffers — Windows UTF-16, а не предположение о размере host c_wchar на Mac. Layout/signature tests отдельно от native behavior.

`_jobs.OwnedJob` выдаётся только native factory, process-local uncopiable capability, constant repr. `create_job(active_limit)` принимает exact1 или2; unnamed/non-inheritable, KILL_ON_JOB_CLOSE|ACTIVE_PROCESS, прочие limits zero, никакого breakaway/UI limit. После Set — readback обязательных flags/active count limit; ошибочный readback исключает create. `active_count()` читает BASIC_ACCOUNTING; `terminate()` делает максимум один запрос с fixed code74, повтор coalesced, ошибка sticky H; `close()` invalidate-before-close, без retry по прежнему числу. Job.empty не заменяет retained process wait. [Job lifetime](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [query](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject).

S единолично хранит J_attempt(limit2); G — J_model(limit1). G при creation получает J_attempt через JOB_LIST; M наследует цепочку G и получает J_model через JOB_LIST. J_attempt не передаётся G даже для query, J_model не передаётся M/S. G проверяет membership M в собственном J_model, S — G в J_attempt; nested inheritance проверяется native suite, отсутствие outer HANDLE у G не обходится временной передачей. [Nested jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs).

`_spawn` имеет один spawn mutex на процесс. До вызова prepared job + explicit temporary inheritable duplicates + HANDLE_LIST/JOB_LIST + fixed stdio; originals не меняют inherit bit. Все arrays/attribute storage/command/env buffers живут до фактического возврата native call, DeleteProcThreadAttributeList только для успешно initialized list. На любом завершившемся вызове временные duplicates закрываются ровно один раз; close failure H, никаких recycled-handle retries. Обычные handles/returned process/thread non-inheritable. Нельзя дополнительно вызвать Popen/shell/blanket inheritance.

Native success немедленно записывает **оба** retained handles в уже зарегистрированный holder до membership checks, cleanup temporary duplicates и любого следующего I/O. Пустой/alias/sentinel output означает unknown, а не guessed ownership. При подтверждённом output wait/terminate разрешены только на этом process handle. Close primary thread после единственного resume или после отказа от запуска; process handle сохраняется до wait proof. На Stop/membership failure до resume — no GO, один TerminateJobObject и, **только если membership не подтверждено**, один TerminateProcess по retained process handle. Это cleanup потенциально не назначенного suspended process, не fallback после ошибки Job kill. Если IsProcessInJob вернул TRUE, TerminateProcess не используется. Ошибка любой операции sticky H; exit proof позже может разрешить закрытие ресурсов, но не clean outcome. TerminateProcess тоже asynchronous; нужен signalled wait. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess).

Общая private единица `_spawn.SpawnRecord` создаётся до native call, содержит creation outcome, in-flight latch, owned PI/attribute buffers, membership/resume/terminate latches и exit observation. Один record на G в S, один на M в G; не более одного незавершённого record на процесс. Его держит strong registry независимо от локального stack/caller reference. Record освобождает native storage после завершения вызова, handles после proof; неизвестность сохраняется до конца процесса. G model creation использует те же правила, а не отдельный незащищённый CreateProcess. Приватные методы можно организовать внутри разрешённых модулей; публичная поверхность holder ниже фиксирована.

## 4. Launch API и lifetime holder

`_launch.prepare_fixture_guardian(slot:SlotLease,binding:WireBinding,*,deadline_ns:int,lease_ns:int,mode='success')->FixtureLaunch` проверяет issued live slot, exact WireBinding, detached UUID values, int nonbool `0<L<=D<2**63`, closed mode enum. Никаких user path/argv/env/reply. Invalid input до native mutation. Возвращает process-local issued uncopiable holder **до** setup/create. Registry strongly retains не более одного незавершённого holder в процессе; второй prepare→runtime_busy. Потеря caller reference не теряет handles. Slot принадлежит caller; reference удерживается, но не close/release/abandon.

Методы holder:

| API | Семантика |
|---|---|
| `start()->None` | Ровно один вызов на launch-owner thread: clock/live bounds, setup pipes/events/Job, create G/membership/resume. Отказ — sanitized WindowsRuntimeError, **holder остаётся доступным и retained**. Нет create retry |
| `request_stop(*,hard=False)->None` | Любой thread: monotone R/H latch, signal соответствующего manual-reset event, если уже создан. До start не создаёт event/process. H sticky, ошибка SetEvent также H. Нет wait/close/SQL |
| `channels` | Readonly record после успешного start: E2 endpoints `control` write, `request` write, `events` read, `status` read, `armed` read. Это borrowed references на issued endpoints, raw integer не authority |
| `poll_process()->LaunchObservation` | На launch-owner thread, nonblocking. Clock/Stop, teardown по правилу ниже; wait G с timeout0, code только после signal; outer count. До start не создаёт OS objects |
| `finish_close()->bool` | На launch-owner thread, nonblocking. True лишь если исход create известен, известный G завершён/outer empty либо штатно не создан, всё собственное I/O quiescent и все собственные handles закрыты. Иначе False; ошибки safe/sticky, registry и slot reference остаются. Не подтверждает M status/SQL |

`LaunchObservation` immutable, без handles/paths/text: `creation` = not_started/failed/created/unknown; `process_exited:bool`, `exit_code:int|None` (signed32), `job_empty:bool`, `resources_closed:bool`, `hard_fault:bool`. Отсутствие process не означает process_exited; false/None остаются до evidence. Ошибки query/wait не дают terminal success. После закрытия хранится snapshot, повторные polls не обращаются к бывшим HANDLE. Unknown не сбрасывается последующим count0 и не допускает успешного finish_close; quarantine может завершиться только внешней процедурой будущего recovery, не пересозданием Python object.

До G resume holder применяет initial D/L перед каждым разрешением следующего шага. После успешного start прежний L **не** используется как текущий lease: дальнейшими permits владеют G и будущий E4 dispatcher. Holder сохраняет D и проверяет его; E4 обязан вызвать request_stop при потере актуального lease. Ordinary R сначала сигналит G, S даёт ему максимум5s continuous от первого наблюдения R в launch loop; затем один outer terminate. H/ошибка clock/startup — outer terminate без grace, но лишь после возврата create. Этот5s предел относится к cleanup, не продлевает анализ. Если G уже вышел, но outer count ненулевой/не удалось прочитать — H и немедленный outer terminate; при обычном G exit/count0 лишний kill не посылается. Повторный poll не переякоряет grace. Если clock потерян, terminate once и nonblocking wait, без придуманных timeout readings. `finish_close` не ставит R на natural-exit path: живой G означает False, caller инициирует Stop отдельно.

Нет публичного factory из PID/HANDLE/DTO и никакого finalizer, закрывающего ресурсы на GC. `start`, process poll и finish_close принадлежат одному launch thread; E4 использует один retained launch/cleanup worker, не выполняет CreateProcess на Stop/control dispatcher. Окончательное `.close(timeout=5)` E4 будет координировать эти операции и I/O threads, не перенесёт их под один чужой mutex.

## 5. Передача handles и I/O threads

S создаёт пять E2 pairs (control/status/armed/request/events) и R/H events. G получает только: control reader, status writer, armed writer, request reader, events writer, slot duplicate, R/H wait-only duplicates, NUL stdin и NUL stdout/stderr. HANDLE_LIST содержит уникальные objects/values; stdout и stderr могут указывать на один разрешённый NUL handle. Owner/root pins/Job handles/противоположные endpoints/родительские pending events не наследуются. Event duplicate G имеет SYNCHRONIZE без EVENT_MODIFY_STATE.

G создаёт prepared/gate/diagnostics pairs. M получает slot, request reader, events writer, prepared writer, gate reader, synchronous diagnostics writer и NUL stdin; stdout/stderr указывают на diagnostic writer. G не держит model-side request/events/prepared/gate/diagnostics handles после завершённой передачи. S аналогично закрывает G-side originals и temporary duplicates; иначе EOF недостоверен. До M creation request/events остаются **неиспользованными**: G не читает и не начинает I/O на них.

`_adopt` — private child-entry boundary: один fixed role table, canonical distinct unsigned handle integers (не0/-1/pseudo), bounded argv, GetHandleInformation, направление/type pipe через GetFileType/GetNamedPipeInfo, DISK slot, CHAR NUL. Очистить HANDLE_FLAG_INHERIT у inherited originals **до** следующего spawn; G создаёт собственные временные duplicates для M. Роли events заданы trusted allowlist; wait-only rights проверены при создании duplicate и native negative SetEvent test, не выдуманным публичным GetEventType. Эти проверки не являются защитой от malicious same-user caller.

Принятый raw handle оборачивается в один OwnedHandle; private adapter может конструировать E2 PipeEndpoint через существующий module-private issuer с fixed kind/synchronous, **без изменения E2**. Это разрешённая точка композиции, не выдача parent API для произвольных integers. Adoption в новом процессе создаёт новый wrapper; это не перенос Python endpoint/thread из parent. Невалидная/повторная роль не закрывается дважды; startup error прекращает child без свободного текста.

| Ресурсы | Единственный I/O owner |
|---|---|
| Setup connect, включая ошибку factory и retained pending | Поток, вызвавший setup; до handoff явно reap, никаких чужих poll |
| S control writer | Будущий E4 control dispatcher, с первой begin_write до close |
| S request/events/status/armed | Будущий E4 data pump, с первой submission до close |
| G control/status/armed/prepared/gate/diagnostics | Один G loop; нет pipe reader thread, мешающего его watchdog |
| M gate reader | Gate watcher thread; он же cancel/poll/close этого endpoint |
| M prepared writer, request reader, events writer | Главный M thread; synchronous diagnostics не через E2 begin_write |

E2 после успешного setup освобождает connect thread ownership; только тогда endpoint можно передать ещё не начавшему I/O owner. После первой пользовательской submission `_io_thread` не сбрасывается. Holder.finish_close может закрывать endpoint без owner или на своём owner thread; foreign-owner endpoint только проверяется как уже закрытый, иначе False и команда владельцу. Close failure остаётся error; чужой wait set не трогаем. Parent Stop только latch/events/cancel; poll pending/event close выполняет тот же I/O owner.

При failed setup orphaned pending registry E2 явно обслуживается launch thread через reap_pending; до completion никакого освобождения OVERLAPPED/buffer/event. G/M выполняют то же правило в своих loops. Если completion не наступил, record и slot/admission остаются занятыми; не выдавать успешный cleanup по одному cancel. Controlled G termination освобождает kernel resources G, но не превращается в подтверждение M wait и не чистит оставшееся S I/O.

## 6. Entry, bootstrap и guardian

Absolute current project interpreter для fixture, fixed trusted entry paths из package location, фиксированный cwd; `-I -B`, shell отсутствует. Mutable Windows-quoted command line, explicit lpApplicationName, `EXTENDED_STARTUPINFO_PRESENT | CREATE_SUSPENDED | CREATE_UNICODE_ENVIRONMENT | CREATE_NO_WINDOW`, STARTF_USESTDHANDLES с тремя валидными handles. Environment создан заново: SystemRoot/WINDIR из bounded GetWindowsDirectoryW; фиксированные Python encoding/locale значения только если нужны fixture. Никаких inherited PATH/PG/proxy/PYTHONPATH/PYTHONHOME/API keys/TEMP. Unicode buffers и argv bounded, user content/request/spec отсутствуют. Imports не загружают DLL/секреты/БД/сеть; entries выполняются лишь под explicit main guard.

`_bootstrap.TokenReader(kind,eof_required=True)` — Windows-local pure parser: prepared=`AIRA-N1P`, gate=`AIRA-N1G`, armed=`AIRA-N1A`, каждый8bytes. feed/finish/ready, cap8, invalid prefix/extra/early EOF poison. Prepared/armed требуют token+EOF; gate принимает token без EOF и далее EOF/extra означает stop. Не импортировать macOS bootstrap и не менять C1C.

G до M проверяет clock и initial D/L, C1C permit seq0 с точным initial D/L, events и control EOF. `D<=now+300s`, `L<=min(D,now+15s)`; now>=old L/D прекращает до decode buffered permit. Один M, no retransmit/renewal после Stop. Отмена без M даёт EOF status и nonzero G exit, без выдуманного M exit code. Все дальнейшие renewals/seq/caps — frozen C1C.

M начинает gate watcher до prepared: локальный bounded handshake подтверждает, что watcher принял свой endpoint, одного Thread.start недостаточно. M не читает request/не импортирует fixture до GO. G допускает GO лишь после exact prepared+EOF, повторной проверки clock/events/control/actual early M exit. После полного GO write отправляет armed+EOF; S/E4 передаёт run лишь после exact armed+EOF и свежего live budget/no Stop. M требует run+EOF и binding/digests, затем импортирует fixture. Initial D/L ограничивают pre-GO; после GO guardian отвечает за lease, watcher — cooperative дополнительная защита. Gate watcher не обещает победить захваченный GIL. При штатном выходе главный M thread просит watcher завершиться, тот cancel/reap/close своего endpoint; bounded join без закрытия HANDLE из main. Неподтверждённый shutdown watcher исключает normal fixture exit.

Ordinary Stop R закрывает gate и запрещает GO, grace<=2s continuous от первого Stop; H/clock fault — немедленный запрос terminate. Grace не даёт новые permit/budget. G loop waits<=100ms, wait set<=32 уникальных retained handles (process, R/H, свои pending events), lanes<=64KiB/turn и<=256KiB суммарно, Stop/clock до payload. Wait set строится заново после reap; уже latched R/H и signalled process после фиксации exit убираются из него, иначе manual-reset event создаст spin. Event не закрывается другим thread во время wait. Для пустого wait set — bounded sleep, не invalid native wait/count0. Timeout — только wakeup, clock проверяется снова. Уже обнаруженная ошибка остаётся H; отсутствие prepared/armed или допустимый partial prefix после принятой отмены само по себе H не создаёт. Не ждать отсутствующий bootstrap ACK при Stop.

Для закрытия M: signalled retained process wait, actual GetExitCodeProcess, J_model.ActiveProcesses=0, диагностика EOF без превышения64KiB. Error/query failure→H; count0 или terminate success отдельно не proof. DWORD преобразуется signed32;259 после signalled — настоящий exit code. После proof закрыть G slot duplicate и model-side ресурсы; failed close/I/O quiescence исключают clean. Tail drain/status send каждый<=2s continuous; clock fault — максимум один nonblocking status attempt, никаких бесконечных ожиданий. Неполученный proof: status EOF без closed(cleanup=True), G exit nonzero, закрытие собственного Job как emergency teardown.

С actual M proof: H→closed(crashed,actual,True), иначе R→stopped, иначе code0→clean, иной code→crashed. Закрытие gate само по себе не H при R. G выходит0 только после успешного полного closed+EOF и успешной очистки своих ресурсов; иначе nonzero. После отправки status последующая ошибка может изменить G exit; E4 проверяет оба факта. При неизвестности/отсутствии M не изобретать code0, новый wire kind или ложный closed.

Fixture modes closed: success/wait/native_hang/result_hang/nonzero/tail/error/diagnostic_flood/early_exit/prepared_missing/prepared_extra/exit_259/exit_ntstatus. Reply ровно `b'fixture-response'`, не B1 анализ. Normal ready/loading/analyzing/result; error adapter_error. Native GIL hold bounded<=5s (например явно typed PyDLL Sleep), обычный wait также<=5s; no infinite fixtures/no model/no network/no subprocess. NTSTATUS mode завершает **себя** fixed DWORD0xC0000005 через ExitProcess, не создаёт настоящий memory fault/диалог/WER. 259 self-exit аналогично. Self ExitProcess — только fixture, не новый способ parent cleanup.

## 7. Acceptance и handoff

До реализации подготовить/проверить collection новой acceptance, frozen commit, настоящий red из-за отсутствующих E3 modules. Не изменять старые tests. Негативные сценарии проверяют сохранность ресурсов/отсутствие повторного spawn и GO, не только поля DTO.

Portable matrix: inert imports; exact ABI/flags/rights/attribute lifetimes; hostile scalar/forged/stale/foreign-process capability; FALSE vs exception vs incomplete TRUE; output retained до последующего fault; все membership/resume исходы, no double resume/kill/close; Stop до start и в native-call barrier; никакой close arrays/Job пока call in flight; Job limit mismatch; exact HANDLE_LIST/no Job/owner leaks; alias roles; minimal env/UTF-16/quoting. Thread matrix E2 неизменна, failed connect strongly retained, launch/pump/control разные owners. Registry cap1, GC, reuse numbers, close/query/wait errors; zero Job count не лечит unknown. Token prefixes/EOF/extra/cancel; permit stale/seq/binding; error priority; signed exit259/NTSTATUS; bounded diagnostics/status; child before GO/request не импортирует fixture. Отдельный тест показывает, что resources closed **не** становится SQL acknowledgement/result candidate.

Native ordinary suite на Windows: real two nested Jobs/JOB_LIST; actual allowlist and reduced-rights event; valid fixture exchange; Stop до resume/GO, request backpressure, GIL hold/result hang; early/bad prepared; diagnostic tail flood; G death после известного create; exact wait/count0/slot release; incompatible external Job fail without fallback; active-process limit rejects descendant;100 attempts HANDLE/thread no growth. Никаких document bytes/реальных весов; retained own handles для наблюдения/cleanup. Нормальные harness cleanup должны сохранить caller slot до physical proof и own I/O completion. On Mac native tests skip с честной причиной, не pass.

**Pre-return death — отдельный обязательный crash gate в disposable Windows VM**, не автоматический тест на рабочем компьютере. Harness не держит extra J_attempt/J_model HANDLE, не добавляет внешний safety Job, меняющий иерархию/last-close. Сам S запускается с retained process HANDLE; наблюдения synthetic, без PID kill. Детерминированные barriers до entry и после return проверяют свои границы; random termination при незавершённом create называется stress, не точным доказательством внутреннего cut point. Неизвестный child нельзя безопасно найти/убить по имени: очищать весь disposable VM snapshot/полной перезагрузкой VM. Без готовой внешней процедуры очистки тест не запускается. Оставшийся неизвестный outcome/утечка — fail/release blocker, не successful cleanup по одному освободившемуся slot. Отдельный physical suspend/resume case также остаётся native gate. Portable mocks этот gate не закрывают.

Реализация: targeted/own, full `bash scripts/check.sh`, source/tests hash до/после, read-only snapshots main V8, result/local commit. Windows-результаты записывать отдельно от Mac gates. **Следующий режим Sol6.1 High, ID D03-17C1E3**; E4 — следующий отдельный цикл после available E3 gate, если новых противоречий нет. Не дробить E3 на дополнительные ID только из-за списка файлов. Самостоятельный остаток **28–43**: этот design готовит уже учтённый E3, не объявляет его реализацию завершённой.
