# D03-03 — результат ручной правки фрагмента DOCX

30 октября 2026. Реализован [контракт D03-03](d03-03-contract.md), часть F05/F10/F11/F12 [текущего объёма](current-product-scope.md). **Общий `bash scripts/check.sh`: 1382 теста и 24 подтеста проходят**, Ruff и форматирование проходят. Пользователь выбирает существующий текстовый фрагмент, меняет его, явно сохраняет и скачивает DOCX с внесённой правкой. Это ограниченный редактор отдельных spans, не полный редактор Word.

## Поведение

POST `/docx-documents/{document_id}/text-edit` принимает строгий ограниченный JSON с точной строковой ревизией хранения, source anchor, ожидаемым и новым текстом. Raw-тело не превышает 2 MiB; тип/encoding/длина/дубли заголовков и JSON-ключей проверяются, NaN/Infinity/не-UTF8 JSON запрещены. Каждый текст ограничен 100000 Unicode-символов. Разбор и валидация запроса, чтение, экспорт и сохранение исполняются в threadpool.

Существующий get_docx проверяет scope и целостность. Сначала сверяется ревизия; неизменный D02-03 export_docx применяет один TextEdit, сохраняя нетронутые части и оформление. Затем неизменный save_docx повторно проверяет ту же ожидаемую ревизию под блокировкой. Конкурентный writer между чтением/экспортом и записью не затирается. Неверные anchors/source/expected text и protected/tracked/signed ограничения не обходятся. Receipt возвращает метаданные завершившегося save, без повторного чтения и с точной строковой BIGINT-ревизией.

В UI text-spans выбираются кнопками, в том числе внутри таблиц. Открывается подписанное поле и явные действия сохранения/отмены. Unchanged-текст не отправляется. Введённый текст и исходная ревизия сохраняются в памяти при отказе, конфликте или неподтверждённом сохранении; принудительной перезаписи нет. После подтверждённого сохранения обновляются сведения/список/view; сбой последующего чтения не отменяет факт сохранения.

Переход с dirty-текстом к другому фрагменту/документу открывает HTML-dialog «Остаться / Отбросить правку». Обе ветки проверены в браузере. Закрытие/перезагрузка страницы дополнительно защищены стандартным beforeunload; нативное предупреждение ОС отдельно не проверялось. Загрузка другого файла недоступна при открытой правке. Скачивание при dirty-тексте предлагает сначала сохранить/отменить. Отмена меняет только локальное поле и не пишет документ. Browser storage и внешние сервисы не используются.

## Приёмка и разрешённое исправление примера

Подготовительный коммит **`2d9a657`** зафиксировал контракт, **52 новых случая** и одно заранее добавленное имя маршрута в старый строгий список. Окончательный красный целевой прогон: **51 failed, 2 passed**, 3 предупреждения, 12,04 секунды. Одна ошибка входила в сам rich-пример: поиск отдельного `warmth` в файле с единым span `Kitchen warmth` останавливал тест до edit-запроса. Поэтому весь красный результат не приписывается отсутствующей реализации.

Первый целевой прогон реализации: **1 failed, 58 passed**, 4 предупреждения, 10,00 секунды; единственная ошибка — этот StopIteration в тестовом примере. После объяснения Никита прямо разрешил «Да, исправить тестовый пример». Изменены только две строки его данных/ожидаемого результата: полный `Kitchen warmth` → `Kitchen heating`; проверки исходника, 19 частей, receipt, stale CAS, view и нового engine сохранены. Исключение записано в контракте. Остальная приёмка и критерии не менялись.

Первый общий gate после исправления: **1382 passed, 24 subtests**, 62 предупреждения, 133,16 секунды. После замены блокирующего нативного confirm переходов на проверяемый HTML-dialog повторён общий gate: **1382 passed, 24 subtests**, 63 предупреждения, **143,00 секунды**, exit 0. Ruff и форматирование прошли, предупреждения не подавлялись. Логи `.runtime/d03-03-frozen-red.log`, `.runtime/d03-03-targeted.log`, `.runtime/d03-03-full-check.log`, `.runtime/d03-03-final-check.log`.

Проверены Unicode/точные пробелы, no-op и последняя допустимая BIGINT-ревизия, строгие типы/path/JSON, scope, недоступность и неожиданные ошибки хранения, body-limit/раннее прерывание/обрыв передачи, protected content, работа вне event loop и финальная CAS-гонка. Старые storage/DTO/проекция/экспорт, прочие API, schema БД, зависимости и runner не менялись.

## Браузер и визуальный экспорт

В собственном disposable preview через браузер выполнены загрузка synthetic rich-source.docx → выбор ячейки `Kitchen warmth` → ввод `Kitchen heating` → сохранение → новый view → скачивание. После обновления страницы и повторного открытия отображается сохранённая правка. При dirty-тексте скачивание заблокировано. В подтверждении перехода «Остаться» сохранило исходный draft, а «Отбросить правку» открыло выбранный другой фрагмент.

Отдельный синтетический writer через существующий PUT сохранил те же bytes с ревизии 2 на 3, пока UI удерживал draft на ревизии 2. UI-save получил конфликт, сохранил `Kitchen my unsaved choice` в textarea и показал объяснение. После явной отмены и повторного открытия серверный документ по-прежнему содержит `Kitchen heating`; чужая свежая запись не затёрта.

Скачанный реальный экспорт: **48129 bytes**, SHA-256 `6d199e32c709ce40d081c89f75c0b734b22813ec0d561e074045b9f839173f90`. Все **19 нетронутых частей** совпали с исходником побайтово. Файл `.runtime/d03-03-qa/edited.docx` — копия браузерной выгрузки; контроль `.runtime/d03-03-qa/export-check.json`.

Через навык Documents фактический экспорт и исходник отрендерены одним bundled LibreOffice. Единственная страница экспорта просмотрена в исходном разрешении: таблица, изображение, списки, начертания, ссылка и колонтитулы сохранены, обрезок/наложений нет. Сравнение двух PNG размера 1547×2002 показало различие только в области изменённой ячейки, bbox `(496, 930, 578, 955)`. QA-рендеры `.runtime/d03-03-qa/rendered/`, `original-rendered/`, сравнение `render-comparison.json`. Microsoft Word не проверялся.

На ширине 390 пикселей панель не создаёт горизонтального переполнения; viewport сброшен. Screenshot `.runtime/d03-03-qa/editor.jpg` показывает рабочую панель с сохранённым текстом. Полный снимок `.runtime/d03-03-qa/editor-desktop.jpg`. QA использовал только синтетические данные, не рабочий архив.
