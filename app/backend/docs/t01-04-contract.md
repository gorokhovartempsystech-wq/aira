# T01-04: следующие версии и локальная идентичность

Этот цикл завершает T01: прикладное создание следующих версий, изоляция двух пользователей и GET /me. Не добавляет HTTP-запись новых версий, Merge/apply, ML, настоящий вход или новые таблицы/миграции. Контракты T01-01/02/03 сохраняются, кроме добавления /me в набор маршрутов.

## Слой хранения

Публичная функция `ara.documents.storage.append_version(runtime, *, document_id, expected_version_id, content_markdown) -> VersionResponse`. Runtime — существующий DocumentRuntime; оба ID — UUID, content — строгая строка с теми же ограничениями, что при POST /documents. Валидация действует при прямом Python-вызове, без HTTP. Неверные ID/текст → безопасный DocumentError со status=422, code=validation_error, retryable=false. Существующий `ara.documents.api.DocumentError` остаётся доступным; ошибки функции того же типа и с теми же публичными полями status/code/message/retryable.

Один вызов владеет одной новой Session и транзакцией, не закрывает engine вызывающего кода. Порядок: проверить проект и владельца серверного runtime (с блокировкой от изменения владельца); найти документ только в этом проекте и заблокировать его строку FOR UPDATE; затем сравнить current_version_id с expected_version_id. Несуществующий/чужой документ или неправильный владелец проекта → тот же безопасный 404/not_found, что в API. Проверка доступа предшествует сравнению версий и не раскрывает идентификаторы чужой истории.

Несовпадение с текущей версией → 409/version_conflict/retryable=false; сообщение без содержимого и идентификатора актуальной версии. Не создавать новую строку. После успешного вызова повтор со старым expected тоже даёт 409, не дублируя версию. Это проверка устаревшей базы; идемпотентность будущего apply с ключом операции относится к T03.

При совпадении создать новую DocumentVersion с новым ID и parent_version_id=expected_version_id, дословным content_markdown, новыми блоками через существующий splitter, provenance={"source":"manual"}, import_omissions по правилам T01-03. Обновить только current_version_id документа и зафиксировать оба изменения одним commit. Вернуть VersionResponse после commit. Title, source_url и все поля предыдущих версий не меняются. Изменение возвращённого Python-объекта не должно изменять сохранённые данные.

При отказе записи версии или обновления current не остаётся новой версии, current и старая история сохраняются. OperationalError → DocumentError 503/storage_unavailable/true, прочие ошибки БД → 500/storage_error/false без SQL, DSN и входного текста. Вызовы с одной базой, пришедшие одновременно, дают ровно один успех и один 409; потерянных обновлений и второй дочерней строки нет. Произвольные UPDATE/DELETE SQL владельцем БД здесь не запрещаются: гарантия относится к прикладному пути, не к отдельному неизменяемому хранилищу на уровне ролей/триггеров БД.

## GET /me и локальный режим

GET /me доступен только в приложении с явно переданным DocumentRuntime. Ответ 200: ровно `{"user_id":"UUID","project_id":"UUID","environment":"local","auth_mode":"local-dev"}`. Пользователь и проект берутся из runtime, существование проекта и соответствие owner проверяются в БД тем же способом, что у маршрутов документов. Нельзя подменить ответ headers/query; при неправильном runtime → согласованный 404, при недоступной БД → безопасный 503. Заголовок X-ARA-Auth-Mode: local-dev обязателен. Ни email, ни реальная сессия не изобретаются.

Автономный create_app() без runtime оставляет только /health и не импортирует DB-библиотеки. DocumentRuntime принимает только mode=local. Дополнительная защита HTTP-фабрики: если ARA_ENVIRONMENT явно задан и не равен local, create_app(document_runtime=...) отклоняет запуск через ConfigurationError до обращения к БД. Отсутствующее значение допускается только для явно внедрённого серверного runtime (тестовый/встраиваемый путь). create_local_app() по-прежнему требует явно заданный ARA_ENVIRONMENT=local; это проверяется до чтения настроек. Импорт модулей остаётся инертным, секреты не читаются при сборке приложения. Проверка одного несекретного флага окружения в явной ветке runtime допустима.

Подготовленная команда `bash scripts/dev.sh --documents` остаётся loopback-only, не принимает host клиента, отклоняет пилотное окружение и не меняет настройки родительского процесса. Настоящую аутентификацию и пилотный сервер этот цикл не реализует.

## Независимая приёмка и границы

Реальная PostgreSQL в отдельных ara_check_<uuid>: цепочка трёх версий с повторным HTTP-чтением всех снимков после пересоздания app/engine; изоляция двух владельцев и разных проектов; откат обоих отказов; stale/repeat conflict; два одновременных writer с одной базой. Отдельно проверяются /me, подмена headers/query, закрытие локального режима в pilot, прежняя инертность health-only и loopback launcher. Новые приёмочные тесты перед реализацией должны падать.

Разрешено редактировать: `src/ara/documents/**`, `src/ara/app.py`, `src/ara/local.py`, `tests/documents/**`. Запрещено менять независимые tests/acceptance, модели/миграции, config/db, зависимости, launcher/runner, задачи и этот контракт. PostgreSQL перед циклом уже работает. Использовать стандартные разрешения для сокета; команда проверки `bash scripts/check.sh`. Не переходить к T02.
