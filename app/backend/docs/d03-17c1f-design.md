## 2. Владение, полномочия и ресурсы

S — единственный supervisor для одной установленной пары private OS root + локальная БД. При старте получает прежний OS owner, при запуске проверки — execution slot. Разные UUID в запросе не создают новый installation/slot. Один активный attempt, один retained publisher на attempt, нет warm pool. G/M не получают engine, connection, URL БД или секреты. Public construction/import не запускают работу; явные start/shutdown, никакой зависимости от polling UI.

S принимает только заранее настроенные локальные `DocumentRuntime` и scoped команды; в первой композиции один runtime. Старый глобальный `claim_next(engine)` **не вызывается**: он может захватить чужую/не зарегистрированную в S очередь и потерять enqueue anchor. Новая функция claim_exact получает runtime/document/run и проверяет связь в БД. Нельзя сделать local Stop чужой работы по входному UUID: быстрый Stop доступен только уже привязанному owned attempt; остальные запросы проходят scoped SQL.

Три независимых результата: **physical evidence**, **RAM permit**, **durable SQL outcome**. `resources_closed`, `candidate_ready`, ACK записи permit в pipe и SQL `succeeded` не заменяют друг друга. Slot не переиспользуется до доказанного физического завершения, завершения всех собственных launch/I/O jobs и SQL reconciliation. При неизвестном create удерживается holder, запрещены второй запуск и поиск/убийство процесса по PID или имени.

Для F3 заранее фиксируются постоянные job lanes: **admission**, **SQL control**, **publication/reconciliation**, **platform lifecycle**, **platform control**. На lane максимум один выполняемый job и один result cell, без очереди будущих jobs, overflow threads или auto retry в executor. Publication и reconciliation никогда не параллельны; admission source preparation отдельно от heartbeat. SQL lanes имеют по одному connection capacity, `max_overflow=0`; максимум3 соединения S. Новые вызовы при busy получают safe busy, stage/tick/Stop coalesce. Platform driver сохраняет собственных владельцев I/O из D/E; S не poll/close их чужим потоком.

Метаданные очереди ограничены16 активными IDs; тяжёлые source/attempt/reply только у одного активного attempt и одного admission job, без копии source для каждого queued run. Документные payload/пути/handles/SQL/exception strings не попадают в view/log/errors. Новые safe error codes для инфраструктуры отделены от frozen SQL run status/error allowlist. Нельзя записать `quarantined` в Run вместо предусмотренного terminal status.

## 3. Время, Stop и публикация

Один dispatcher вызывает все переходы C1A. Никакого SQL, DOCX parsing, codec, callback, process wait/renew/close под его mutex. Clock — native continuous (Darwin continuous / Windows GetTickCount64), integer ns, включает сон; `time.monotonic()` сам по себе не платформенное доказательство. Перед каждым переходом новый sample. Порядок поступивших caller timestamps не становится порядком переходов.

Anchor `e` берётся до enqueue. Новая работа получает неизменяемый `D_enqueue=e+300s-guard`. Перед claim берётся `s`, после SQL ACK — `r`; C1A budget из `deadline_at-claimed_at`, `lease_expires_at-claimed_at`, затем D ограничивается прежним `D_enqueue`, L ограничивается D. Guard50ms применяется один раз. Временные разницы datetime переводятся целочисленно, без float. Просроченный ACK не даёт запуск; неизвестный ACK не даёт повторный claim/inference. Retry — новый run/key и новый enqueue anchor, idempotent replay прежнего key не обновляет D.

Heartbeat примерно раз3s, tick не реже250ms, reaper примерно раз1s; это scheduling policy, не гарантия ОС. Новый SQL receipt несёт **heartbeat_at из той же транзакции**, lease и exact identity/fence. Frozen `WorkerUpdate` этого времени не содержит, поэтому F2 выдаёт отдельный receipt, не вычитает wall clock клиента и не расширяет старый DTO. Перед запросом `s_h`, ACK `r_h`; bound=`s_h+(lease-heartbeat_at)-guard`, clamp D. При обработке dispatcher использует свежее время, поэтому даже своевременно пришедший, но поздно обработанный ACK не оживляет истёкшую L. Bound ниже прежней L не принимается; не устраивать циклические retries ради продления.

После принятия SQL receipt C1A может продлить свою L. Platform control job отдельно доставляет этот bound G: Windows `renew(True)` — только своевременный local receipt; False/busy не подтверждает renewal. Допускается повтор **того же** bound в старом live окне без новых SQL heartbeat/anchors; по старой принятой native L — Stop. Mac return/error нормализуются адаптером. Natural completion — отдельная ветка: когда physical/EOF proof получен и candidate захвачен ещё в live окне, G уже не нуждается в renew. C1A/SQL heartbeat для дальнейшей валидации может продолжаться до D. False от уже закончившегося driver не считается новым storage failure. Result queue не продлевает жизнь ранее не принятого candidate.

Stop coalesces в выделенной ячейке, не ждёт свободного DB lane. Platform control lane получает Stop независимо от SQL и codec. Порядок dispatcher: pending Stop/clock cutoff → lease/child evidence → publication request. Mutex admission Stop и reserve linearization согласован: Stop, уже принятый до reserve, запрещает permit. После reserve Stop не обещает `cancelled`: допустим ранее начатый COMMIT. Publisher сохраняет exact reply/token до ordered-lock reconciliation; поздний success не удаляется. Unknown outcome запрещает второй publisher/attempt. Старый `complete_attempt` не используется как запасной путь.

PublicationPort отвечает синхронному C1B через bounded cell; **потеря ответа reserve** отличается от потери SQL COMMIT. Grant сначала offered, caller под коротким cell lock принимает его либо abandons при timeout. Только принятый token может покинуть port. Dispatcher может `settle(rolled_back)` недоставленный token, потому что он никогда не мог попасть в SQL; после принятия такого доказательства уже нет. Потерянный settle ACK не откатывает COMMIT и не теряет pending token. Точные правила F1 находятся в контракте.

Первый сбой storage останавливает compute; повторные чтения для reconciliation допускаются по одному, с coalesced demand и bounded backoff, без нового inference. Долгий SQL вызов не снимается из busy по timeout ожидания caller. Недоступный clock запрещает новый permit/lease, включает Stop; known committed сохраняется даже при сломанном clock. Для такого defensive Stop допустим последний валидный sample, без добавления времени.

## 4. SQL scope, durability и неизвестные ACK

Новые F2 services используют frozen helpers для scope/source/ordered locks и validation, не меняют B3A/B3B. Exact claim повторяет двухфазный source preparation B3B для конкретного зарегистрированного run: тяжёлый capture вне locks, затем fresh ordered-lock recheck и одна атомарная запись attempt/run. Перед этим S уже владеет owner+slot. Совпадение run_id само по себе не позволяет вернуть claim чужому worker. Lost claim ACK читается под тем же ordered lock, а не повторяется как новый claim. Затем отдельная arm transaction сохраняет binding ledger→attempt до OS call. Crash между claim и arm оставляет unlaunched run для startup/reaper; после рестарта old running никогда не возобновляет inference.

Порядок locks остаётся project → document → run → attempt; новый ledger берётся **последним**, когда операция касается и run. Ledger-only операции не ждут run locks. Старый enqueue advisory lock `(1095911745,170301)` только для admission/startup queue snapshot; никакой обратной цепочки ledger→run или долгого parsing под advisory. Результат публикует исключительно C1B с прежними constraints/source identity.

Отдельные явно создаваемые S engines, не mutation общего `DocumentRuntime.engine`: connect timeout2s, pool timeout0.5s, lock timeout500ms, statement timeout2s, idle-in-transaction2s, transaction timeout5s. F2 проверяет PostgreSQL>=17 для последнего параметра; неподдерживаемую версию не принимает молча. Один локальный адрес/endpoint, без DNS/multi-host fallback в обещании2s. Timeout ожидания результата5s лишь переводит S в pending/blocked, не доказывает rollback/смерть worker. Закрытие connection/session выполняет его владелец. Heavy source/result validation вне write transaction; no prepared transactions.

Это настройки новых сессий через connection options; они не меняют сервер глобально. `statement_timeout` действует на statement, `transaction_timeout` — на транзакцию; серверный timeout не доказывает доставку клиенту ответа. [PostgreSQL18: Client Connection Defaults](https://www.postgresql.org/docs/18/runtime-config-client.html). `connect_timeout` задаётся отдельно для каждого host/IP, поэтому не является общим deadline нескольких адресов. [libpq connection options](https://www.postgresql.org/docs/18/libpq-connect.html).

Ledger и result должны быть обычными logged tables, не UNLOGGED/temp. У каждого S connection `synchronous_commit=on`; startup проверяет `fsync=on`, `full_page_writes=on`, primary read/write mode. При неподтверждённой durability — no launch. Это не защита от неисправного диска или восстановления старой копии БД. Смысл ожидания WAL flush и различия `synchronous_commit`/`fsync` следуют из [PostgreSQL18: Write Ahead Log](https://www.postgresql.org/docs/18/runtime-config-wal.html).

Наблюдение 3 ноября: локальный PG18.6/Postgres.app, psycopg3.3.5/libpq180006, SQLAlchemy2.0.54; fsync/full_page_writes/synchronous_commit=on. Это read-only проверка dev окружения, не гарантия будущего установщика. Рабочая БД остаётся V8; V11 испытывается только на отдельных test DB после F2 freeze.

Unknown enqueue: сохраняются тот же key, command и anchor, повторным scoped lookup определяется durable outcome; новый key/300s/launch не выдаётся. Unknown claim: никакой OS create, retained job/identity до согласования. Unknown arm: create запрещён до подтверждения ledger. Unknown result COMMIT: тот же retained C1B publisher/reply/token и ordered-lock barrier. Если original job ещё может писать, новая операция не стартует даже после timeout. SQL terminal не является physical evidence.

## 5. Durable launch ledger и аварийное восстановление

F2 добавляет отдельную migration V11 поверх V10 и singleton ledger **на БД**, не строку на document и не per-request installation ID. Нормативная модель для точного DDL F2: `slot_key=1`, positive bigint CAS revision, phase `unprovisioned|clean|armed|drained`, installation UUID, owner epoch UUID, launch UUID, document/run/attempt/worker UUID и claim_fence1 для armed/drained. Поля binding одновременно NULL либо полностью заполнены; clean/unprovisioned не содержат binding. Для unprovisioned installation/owner NULL; clean требует installation, owner может NULL до первого S. Armed/drained требуют обе идентичности. UUID не являются proof сами по себе. Timestamp только диагностика, не criterion очистки.

Нет FK/cascade, позволяющего удалением document/run снять fence. Новая ledger row переживает terminal/reap и отделена от результата. Она не хранит request/reply, PID, path или секреты. Missing/duplicate/malformed row — blocked, не auto-init clean. Миграция создаёт **unprovisioned** row; downgrade допустим только в unprovisioned, без binding, после lock; clean также не удаляется автоматически, чтобы не потерять факт provisioning. Исключение для первоначального downgrade пустой схемы покрывается explicit unprovisioned состоянием. Точный ORM/DDL и pin старых V10-only migration tests готовятся в F2 parent preparation; никаких blanket изменений assertions/default `head`.

Provisioning — доверенная операция установщика над действительно новой БД/root до любого legacy worker. Это не HTTP endpoint, не кнопка «забыть ошибку», не выбор нового UUID при blocked. Upgrade существующей V10 с историей запусков не объявляет отсутствие старых процессов; до подтверждённого пути миграции остаётся unprovisioned. F2 portable tests используют доказанно новую одноразовую БД. Production provisioning и boot evidence входят в desktop/native release gate, не объявляются выполненными mock receipt.

| Переход | Необходимое доказательство |
|---|---|
| clean → armed | Owned slot, exact claim, fresh live C1A budget; binding+CAS durable COMMIT **до любого вызова create/factory**, включая async Windows и синхронный Mac Popen |
| armed → drained | Тот же живой S: retained actual physical completion/EOF и own launch/I/O quiescence, нет неокончившегося create; либо он точно ещё не вызывал create и завершил/разрешил все pending jobs этой попытки |
| drained → clean | Old SQL terminal/result reconciled, все jobs старого поколения завершены, slot успешно освобождён/проверен под всё ещё удерживаемым OS owner; durable CAS ACK, затем допускается следующий claim |
| armed после crash S | **Quarantine**. Free slot, lease expired, SQL terminal, новый owner UUID, сообщение пользователя о перезагрузке не снимают fence |

После armed→drained receipt может потеряться: живой S делает ordered ledger read, повторяет **тот же** переход/binding, не create. После drained→clean ACK-loss — новый claim блокируется до read reconciliation. После crash с durable drained новый S может закончить SQL reconciliation без модели и очистить ledger, удерживая OS owner; старый S уже отсутствует, slot проверяется отдельно. Если crash был до drained COMMIT, physical knowledge из RAM потеряно: conservative quarantine, даже если процессы фактически закончились. Это осознанная потеря доступности, не ложное доказательство завершения.

Для автоматического выхода из armed quarantine требуется отдельный проверенный boot-generation provider или равноценное платформенное доказательство. В текущем проектировании **такого provider нет**. Uptime, часы, PID, BCD boot-entry ID и переименование root не считаются подтверждением новой загрузки. F2/F3 не имеют reset-by-bool/force-unlock API. Допустима диагностика `recovery_required`; не обещать, что обычный restart/reboot автоматически исправляет это. Native crash/suspend/VM-проверка и production recovery остаются открытым release gate; сама безопасная blocked ветка должна быть реализована и протестирована сейчас.

Trust boundary: один root/DB, без внешнего writer, rollback backup или клонирования установки. Восстановление БД из старого backup требует отдельного provisioning/recovery процесса; не разрешать запуск просто потому, что restored row выглядит clean. Сторонняя запись в БД и администратор ОС не входят в локальную защиту C1F.

## 6. Startup/reaper/shutdown

1. Explicit start получает OS owner, проверяет schema/settings/ledger; до окончания startup barrier admission закрыт. При armed quarantine новые проверки не стартуют, чтение документов/готовых результатов не требует запускать модель.
2. Под прежним enqueue advisory lock снимается bounded набор **старых queued IDs**, после release по одному ordered locks/recheck. Не сравнивать wall timestamps с временем запуска S. Все старые queued прекращаются как interrupted (либо существующий deadline/cancel outcome); новый inference по ним не запускается. Если размер уже нарушает16 — blocked/error, не молча оставить хвост и включить admission.
3. Old running/cancel_requested не переисполняются. Reaper по прежним правилам завершает просроченные состояния; committed success сохраняется и source-backed проверяется. Pending publication прошлого процесса восстанавливается только из durable SQL результата, без восстановления RAM permit/ответа и без новой публикации непроверенного reply.
4. Admission открывается после обработки старой очереди, reconciliation и clean ledger. Зарегистрированные новые queued entries содержат original anchor и scope; неизвестный/не зарегистрированный queued run никогда не украдывается общим claim_next.
5. Shutdown атомарно закрывает admission/claim, coalesces Stop, ждёт собственные jobs до общего5s caller budget. False/pending сохраняет сильные ссылки/ledger/slot; нельзя считать daemon thread завершённым или освободить native handles из чужого потока. Закрытие приложения при pending оставляет armed fence и fail-closed restart. Если всё завершено, reconcile → drained/clean → release owner. Повторный shutdown не запускает новую работу.

## 7. Композиционные проверки F3 и предел доказательства

Каждый cut point проверять barriers/fault injection: enqueue/claim/arm до commit и после commit до ACK; до OS call/внутри неизвестного create/после handle; после candidate до child_closed; Stop до reserve/после offer/после принятия; commit rollback/ACK-loss/settle ACK-loss; physical exit до drained/после drained; clear ACK-loss; crash/shutdown с занятым DB/native job. Проверять отсутствие второго create, неизменный D, capped threads/connections/cells, сохранность SQL success и ledger после удаления документа/смены ownership. Случайный sleep не доказывает гонку.

Portable SQL integration использует явно синтетический ComputePort с **валидным B1 reply**, затем настоящий GuardedPublisher и отдельную test DB. Existing Mac/Windows `b'fixture-response'` не B1: native driver composition отдельно обязана отвергать его как invalid_result, сохраняя physical/ledger cleanup. Нельзя подменить эти bytes валидным ответом в production adapter и объявить native→B1 end-to-end success. Настоящий мост payload/weights — C2; до него оба вида evidence указываются раздельно.

Адаптер захватывает immutable candidate reference, пока driver допускает её выдачу, затем завершает собственную очистку и передаёт child_closed. Это особенно важно для Mac: close/discard удаляет reply из pump. F3 не пытается получить его заново после закрытия и не публикует candidate до остальных gates.

Native Windows E1–E4 skips, Mac Word hidden/revision evidence, installer provisioning и доказательство нового boot не закрываются переносимыми mocks. F3 может завершить available backend composition с явными ограничениями; production startup не включается и full recovery не объявляется готовым. Source нового функционала не должен silently bypass эти gates.
