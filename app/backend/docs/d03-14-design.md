# Разбиение, склейка и отмена изменений DOCX — техническое решение

31 октября 2026. Проектирование на Astra 6 по прямому запросу Никиты после D03-13 / 1b11943. Относится к F05/F11/F12 [основного продуктового документа](current-product-scope.md). Это техническое решение для следующих циклов; функции ниже ещё не реализованы. Полный продуктовый объём DOCX сохраняется, ограничения первого цикла не исключают оставшуюся работу.

## Основание в текущем коде

- D03-11 вставляет/удаляет целые body paragraphs, D03-12 меняет style/list, D03-13 сохраняет такие batches сразу в current DOCX с CAS и durable receipt.
- `docx_package.session.DocxSession` уже хранит точные bytes состояний, undo/redo и saved digest. Сейчас apply принимает только RangeEdit внутри абзаца. История ограничена 100 состояниями / 128 MiB сжатых пакетов; это бюджет истории, а не всей RAM.
- `workspace/static/history.js` хранит текст и выделение одного поля. Он не является историей всего DOCX. `docx_documents/recovery_schemas.py` сохраняет только TextEditRequest и pending operation_id.
- В шаблоне AIRA Heading1 и Normal различаются размером 16/11 pt и другими свойствами; runs не обязаны иметь прямой rPr. У Heading1 задан next=Normal. Это проверено на синтетическом пакете текущим генератором: `.runtime/d03-14-design-probe.json`.

Paragraph style определяет в том числе символьные свойства runs. Поэтому перенос правых runs под левый pStyle способен изменить их вид даже при неизменном run XML. Основание — [Microsoft: paragraph styles](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-create-and-add-a-paragraph-style-to-a-word-processing-document). Наш вывод: сравнения одного прямого rPr недостаточно, а склейка не является надёжной обратной операцией для отмены split.

## Решения

1. Авторитетное состояние — исходный DOCX package и его точные изменённые snapshots. Текстовая проекция нужна для адресации/интерфейса; повторная сборка документа из plain text запрещена.
2. Split/join — отдельные чистые операции. Они не реализуются цепочкой публичных HTTP insert/delete: промежуточное состояние не должно попасть в БД или историю пользователя.
3. Одна пользовательская команда — одна атомарная публикация состояния и одна позиция undo. Любые промежуточные packages существуют только во время вычисления. Ошибка сохраняет исходник, курсор и обе истории.
4. Undo/redo возвращают bytes сохранённых состояний; они не вычисляют обратные split/join и не воспроизводят команды заново. Автосохранение не очищает историю открытого документа.
5. Первый pure join допускает совместимое paragraph formatting. Разные стили не подменяются и не «уравниваются» молча. Расширение на разные стили требует отдельного resolver, умеющего материализовать наследование и проверять визуальную эквивалентность.

## Поведение редактора и порядок доставки

В таблице описано целевое поведение контроллера редактора. Реализуемый первым D03-14 содержит только lossless primitive split/join из отдельного [контракта](d03-14-contract.md); он не перехватывает клавиши и не принимает UX-решения за контроллер.

| Действие | Результат | Одна позиция undo |
|---|---|---|
| Enter в середине обычного абзаца | Левая/правая части без потери символов и выделений; курсор в начале правой | Да |
| Enter в начале/конце обычного абзаца | Пустой абзац до/после текста; курсор в правом | Да |
| Enter посреди заголовка | Обе части сохраняют стиль заголовка, существующий текст не переоформляется | Да |
| Enter в конце непустого заголовка | Новый пустой абзац получает валидный `w:next`; для AIRA — Normal | Да, split + назначение стиля вместе |
| Enter в непустом пункте списка | Новый пункт той же последовательности/уровня, без создания нового numId | Да |
| Enter в пустом пункте списка | Выход из списка в этом абзаце, без создания ещё одного пустого пункта | Да; отдельная политика контроллера |
| Backspace в начале правого / Delete в конце левого | Одна и та же JoinParagraphs(left,right), курсор на стыке | Да |
| Backspace в начале документа / Delete в конце документа | Без изменения; не создаёт undo entry | Нет |
| Shift+Enter | Мягкий разрыв строки внутри абзаца | Отдельная будущая inline-команда, не split |
| Вставка нескольких строк | Один пользовательский шаг, несколько новых абзацев по явно выбранной политике plain-text paste | Отдельный цикл после primitives |
| Enter при IME composition | Подтвердить composition, не выполнить лишний split | Composition — одна текстовая команда |

В D03-14 pure SplitParagraph всегда сохраняет формат обеих частей. Правила next-style, выхода из пустого списка, клавиш/IME/выделений — контроллер следующего цикла. `w:next` относится к следующему абзацу; его смысл описан в [Microsoft NextParagraphStyle](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.nextparagraphstyle?view=openxml-3.0.1). Выбор применять его только к новому пустому абзацу — решение AIRA для сохранности существующего текста, а не заявление о полном повторении поведения Word.

При отсутствующем next контроллер сохраняет стиль. При неверном/неоднозначном next операция отклоняется целиком. Для списков приоритет — продолжение существующего списка; next применяется при выходе из пустого пункта. Нельзя угадывать Normal по имени в импортированном документе: нужен проверенный paragraph default/next и подтверждение отсутствия у него наследуемого списка. Пока такого resolver нет, действие недоступно с объяснением, текст сохраняется.

При несовместимых стилях склейка сообщает «Нельзя объединить эти абзацы с сохранением оформления». Для расширенной реализации требуется доказать сохранение effective run formatting с учётом basedOn, character styles, toggles, темы, default styles и numbering. Простая подстановка font/size или копирование style.rPr не является общим resolver. Разные align/indents/layout всё равно требуют явного правила единого paragraph formatting; текущий primitive не делает этот выбор.

## Адреса и Unicode

Новые команды используют paragraph anchor + Unicode code-point offset. Это позволяет адресовать пустой абзац, TAB и мягкий разрыв; прежний TextPosition адресует только текстовый span и здесь недостаточен. SHA привязан ко всему source package; после изменения нужны новые anchors. `session_revision` различает одинаковые bytes в разных состояниях (ABA), `storage_revision` защищает запись в БД. Эти три значения не взаимозаменяемы.

Frontend переводит DOM UTF-16 offsets в code points и обратно, проверяет границы surrogate pair. Пользовательский курсор дополнительно ограничивается grapheme boundaries (emoji/диакритика не разрезаются клавишами); pure API работает с code points и не нормализует Unicode. На границе двух runs для будущего ввода нужен явный affinity left/right, а не вывод по одинаковому тексту. Для split сам offset определяет место разреза; для возвращения курсора новый anchor читается из post-projection.

Целевые позиции: split → правый paragraph, offset 0; join → сохранившийся левый, offset len(old_left_text). Undo восстанавливает selection до команды, redo — после. Для каждого snapshot selection использует anchors именно его SHA; не переносить anchors заменой одного hash в прежнем path после структурной операции.

У пустого нового paragraph может не быть текстового span. Контроллер адресует его paragraph anchor и хранит typing format/affinity отдельно от отсутствующих символов. Primitive D03-14 не обещает создать пустой styled run для будущего набора; правило наследования ввода и его восстановление вместе с selection фиксируются в D03-15 до реализации. Нельзя выводить это состояние из первого случайного соседнего span.

## История открытого документа

Следующий ограниченный цикл D03-15 расширяет существующий DocxSession методами apply_boundary, apply_structure, apply_formats. Сохранить публичные поля SessionSnapshot, старый apply(RangeEdit), ошибки, limit/eviction/mark_saved и все прежние тесты. Общий private publish-changed путь используется всеми видами правок. Сравнение bytes определяет no-op; no-op/ошибка не сбрасывают redo. Новая фактическая правка после undo удаляет redo.

Контроллер команды должен публиковать составной результат один раз. Нельзя вызвать публичный apply_boundary, затем apply_formats и объявить две сохранённые позиции одной командой. Для Enter-after-heading сначала вычислить обе pure операции в закрытом candidate, подготовить projection и selection, затем принять candidate одной транзакцией истории. Метод принятия candidate — внутренний, не произвольная замена DOCX из недоверенного клиента; его точная сигнатура фиксируется в контракте D03-15 до реализации.

Selection metadata принадлежит позициям общей истории. У каждой позиции собственный локальный ID, bytes hash недостаточно из-за повторяющихся состояний. Вытеснение по лимитам одновременно удаляет соответствующие selections; ошибки подготовки selection/projection не меняют ни один стек. Сессионный DTO D02-05 не расширять случайно ради курсора: controller wrapper держит связанное состояние и проверяет глубины/ID при каждом переходе. Старый single-span history.js сохраняет свой контракт до переключения редактора на новый controller. Один ввод не должен записываться одновременно в две независимые истории.

Все команды одного документа сериализуются, разные вкладки имеют отдельные истории. Обычный ввод можно объединять по прежнему правилу typing groups; split, join, paste, style/list, IME commit и undo/redo закрывают группу. Ctrl/Cmd+Z, Cmd/Ctrl+Shift+Z, Ctrl+Y и browser historyUndo/historyRedo должны вызывать один controller; beforeinput/keydown не должны применять команду дважды. DOM selection сохраняется отдельно от server anchors и проверяется при конвертации.

`mark_saved` подтверждает только успешно сохранённую текущую session revision. Поздний ACK не помечает более новый текст сохранённым. Во время неизвестного исхода durable save контроллер блокирует новые мутации и undo/redo этой вкладки до reconciliation; другие вкладки работают. Это узкая стартовая политика, позволяющая использовать прежний строгий mark_saved без ложного сброса dirty.

## Сохранение, потеря ответа и восстановление

D03-16 — отдельный storage/transport цикл, его миграции и wire schemas здесь не считаются разрешёнными к реализации. Политика: working DOCX и saved current DOCX различаются. Undo изменяет рабочее состояние; если прежняя правка уже сохранена, отмена сохраняется как новое состояние с новой storage revision через тот же CAS. Нельзя уменьшать storage_revision или удалять старый receipt.

Для нового editor-controller все изменения идут через общий working state. Прежние D03-13 commands сохраняют сразу; они не должны параллельно применяться к тому же открытому draft как второй writer без reconciliation. Их успешные записи, как и legacy text-edit/PUT content, считаются внешними относительно рабочего состояния и обнаруживаются по storage revision. Продуктовый endpoint для workspace и миграция выбираются в D03-16 до frozen acceptance; текущие routes не расширяются этим документом.

Требования к durable протоколу:

- Перед отправкой save сохранить локальный checkpoint: source/base storage revision, точные working bytes/hash, selection и неизменяемый pending intent (operation_id, expected revision, candidate digest). Данные остаются в локальном PostgreSQL. Не помещать DOCX в localStorage или журналы.
- Save/undo-save/redo-save используют устойчивый ключ операции. Серверный receipt однозначно связывает ожидаемую revision и точный candidate. Текст/hash сами по себе не доказывают, что именно наша операция была записана.
- Packet update и receipt атомарны под существующим project/document lock. ACK-loss → повтор того же intent, без нового ключа и без повторного split/join. Результат старого replay не заменяет более свежий current.
- После подтверждения обновить base revision, подтвердить сохранённый digest и очистить pending/checkpoint с CAS token; не удалять checkpoint другого окна. Ошибка очистки даёт восстановимый pending, повтор не дублирует запись.
- Несохранённая работа должна checkpoint-иться при переключении/закрытии вкладки и по согласованному autosave каждые две минуты; crash до очередного checkpoint может потерять только ещё не записанный хвост. Обещание zero-loss между checkpoint не вводится.
- При восстановлении проверить package/hash/base и pending receipt. Внешняя новая revision даёт конфликт с сохранением рабочей копии. Автоматическое слияние или наложение старых anchors запрещено.

После перезапуска требуется восстановить последний durable working document, selection и pending intent. Полный undo stack между перезапусками в этом решении не обещается: новый процесс начинает новую историю от восстановленного состояния. История внутри открытой сессии сохраняется при autosave и переключении вкладок. Если потребуется сохранять и весь стек между запусками — отдельное продуктовое/ресурсное решение, не следствие F12.

Предыдущий /draft знает только single-span edit и не может хранить эти bytes/операции. Новый versioned checkpoint нельзя записывать в старый payload без совместимости: старые readers иначе получат 500. В контракте D03-16 обязательны version discriminator, migration/совместное чтение или отдельная таблица с явной арбитрацией одного draft на document. Наличие JSONB не отменяет этого контракта. До D03-16 структурное редактирование не заявляется устойчивым к перезапуску приложения.

## Циклы и критерий готовности

| Цикл | Результат | Критерий выхода |
|---|---|---|
| D03-14 | Pure split/join по приложенному контракту | Frozen positive/negative tests; exact preservation; визуальный экспорт; full gate |
| D03-15 | Единая сессионная история, selection, Enter-policy | Смешанные text/split/join/style undo chains, atomic composite command, no-op/ошибка, budgets/ABA/caret |
| D03-16 | Durable working state, keyed save, recovery, handoff | ACK-loss/crash/concurrency/foreign writer/legacy checkpoints; restart restores confirmed state |
| Следующий UI-цикл совместно с frontend Ани | Клавиши, composition, selection, autosave и ошибки | Проверка сквозного сценария Windows/macOS + целевого Word; без двойного действия и потери данных |

Расширения на несовместимые paragraph styles, multi-level list UX, ячейки/поля/сложные объекты и paste — отдельные задачи после первых primitives. Это технический порядок покрытия исходного объёма, не его исключение. D03-15/16 требуют собственных точных contracts/acceptance до кода; данный дизайн не даёт права за один проход изменить все слои.

Теперь для реализации D03-14 достаточно Sol 6.1 High. Повышать режим повторно стоит только при обнаруженной неоднозначности XML/наследования, а не для обычного запуска тестов. Runner/tasks/progress, зависимости, авторизация и квота этим решением не изменяются.
