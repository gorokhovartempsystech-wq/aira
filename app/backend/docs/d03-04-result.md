# D03-04 — безопасный повтор сохранения DOCX

30 октября 2026. Реализован [контракт D03-04](d03-04-contract.md), часть F05/F11/F12 [текущего объёма](current-product-scope.md). Потеря ответа после записи теперь разрешается повтором конкретной операции. Это один этап надёжности ручного редактора; автосохранение и восстановление после закрытия приложения ещё не реализованы.

## Поведение

Существующий POST text-edit принимает необязательный canonical UUID в Idempotency-Key. Для такой попытки DOCX и подтверждение сохраняются в одной транзакции PostgreSQL. Сначала удерживаются прежние ownership/project lock и общий с другими writers lock документа. Проверяются целостность original/current, исходная ревизия, anchor и expected text. Экспорт и его ограничения неизменны.

Повтор с тем же ключом и содержанием возвращает исходные метаданные операции. Он не редактирует документ и не увеличивает ревизию, включая случай более поздней чужой записи. Перестановка JSON-полей, пробелы и экранирование не меняют semantic fingerprint; другое содержимое с тем же ключом даёт 409 idempotency_conflict. Scope проверяется до поиска подтверждения. Без ключа прежний API сохраняет строгий CAS и старое поведение повторов.

Новая таблица docx_edit_receipts содержит UUID операции, SHA256 запроса и семь полей метаданных сохранения. В ней нет текста запроса или DOCX. Она сохраняется между процессами; replay не зависит от памяти сервера и не определяется по совпадению текста. Результат проверяется и готовится до commit; ответ появляется после commit. Отказ вставки receipt или commit откатывает обе записи. Если реальный commit прошёл, но ACK потерялся, повтор получает сохранённый результат. Повреждённые packages/receipt не выдаются за успех.

В UI первая попытка удерживает ключ и точный payload. После сети/тайм-аута/5xx/некорректного ответа поле readOnly, доступно для выделения и копирования; кнопка «Повторить сохранение» отправляет ту же пару. Известный 4xx оставляет текст и вновь разрешает ввод, не делает принудительную запись. При закрытии неподтверждённой попытки dialog предупреждает о возможной записи и отсутствии отката. После 200 draft закрывается и обновляется view; последующий сбой чтения не отменяет подтверждение. Новых таймеров, browser storage, зависимостей и автоматических повторов нет.

## Проверки

Подготовительный коммит **7e46000** заморозил контракт и 37 случаев приёмки. Исторический migration-тест заранее закреплён на V6 вместо плавающего head; прежние assertions сохранены. До реализации целевой прогон: **36 failed, 1 passed**, 3 предупреждения, 8,42 секунды. После реализации: **2 failed, 103 passed**, 4 предупреждения, 21,37 секунды, включая старые HTTP/storage проверки.

Два отказа были ошибками подготовки тестов: subprocess не получил путь src, SQLAlchemy types сравнивались по идентичности. Никита прямо разрешил «Да, исправить обе проверки». Исправлены только путь импорта и строковое представление типа при сравнении полного описания колонок. Сохранность данных, receipt, ревизий и ограничения БД остались обязательными. Первый общий прогон, уже запущенный до исправления, зафиксировал те же два отказа: **1417 passed, 2 failed**, 24 подтеста, 62 предупреждения, 153,23 секунды. Они не приписываются дефектам реализации.

После исправления новые acceptance и две дополнительные проверки protected content/threadpool: **39 passed**, 3 предупреждения, 8,57 секунды. Полный `bash scripts/check.sh`: **1421 passed, 24 subtests**, 64 предупреждения, 144,41 секунды; Ruff/format проходят. Предупреждения не подавлялись. Отдельно проверен синтаксис app.js bundled Node.

Приёмка включает реальные транзакции с отказом до commit и потерей ACK после commit, rollback при отказе receipt INSERT, конкурентные одинаковые/разные ключи, новый engine и отдельный Python-процесс, scoped replay, semantic hashing, отличие каждого поля запроса, повреждение storage/receipt, no-op на последней BIGINT-ревизии, неизменный CAS без ключа. Миграция сохраняет все прежние synthetic rows/schema/bytes при upgrade/repeat/downgrade; общий gate проверяет совпадение ORM и схемы.

Логи: `.runtime/d03-04-frozen-red.log`, `d03-04-targeted.log`, `d03-04-full-check.log`, `d03-04-corrected-targeted.log`, `d03-04-final-check.log`. Окончательный контроль после уточнения сообщений интерфейса — `d03-04-release-check.log`: **1421 passed, 24 subtests**, 64 предупреждения, **147,65 секунды**, exit 0; Ruff/format проходят.

## Браузер и DOCX

В собственном disposable preview middleware один раз заменил успешный ответ text-edit на 503 **после завершения записи**. UI сохранил `Kitchen heating`, readOnly=true, disabled=false и показал повтор. В БД были ровно один документ ревизии 2 и один receipt. После кнопки повтора ревизия, hash, размер, timestamp и receipt совпали побайтово по JSON-снимкам; UI подтвердил запись и показал новый текст. Снимки `.runtime/d03-04-qa/after-lost-ack.json`, `after-retry.json`; screenshot `retry-pending.jpg`.

После повтора следующая обычная правка `Kitchen heating updated` сохранилась и скачалась. Контрольный экспорт: **48135 bytes**, SHA256 `75139dfb85b9594eb871b392bb0198cc58ecf187be336542e1ccea6e4ff40ba4`; **19 нетронутых частей** совпали с исходником. Файл `.runtime/d03-04-qa/edited.docx`, контроль `export-check.json`. Через Documents фактическая выгрузка отрендерена bundled LibreOffice, единственная страница просмотрена: таблица, изображение, начертания, списки, ссылка и колонтитулы сохранены, наложений/обрезок не обнаружено. Рендер `rendered/page-1.png`; Microsoft Word не проверялся.

Затем synthetic competing writer поднял ревизию 3→4, пока UI держал draft. Save получил 409, текст `Kitchen my unsaved choice` сохранился, readOnly=false; свежая запись не затёрта. После отмены и переоткрытия показано сохранённое содержимое. Отдельная вторая потеря ACK и закрытие через «Отбросить правку» проверили отсутствие обещанного отката: при переоткрытии показан реально записанный `Kitchen heating`. Ветка «Остаться» также сохраняла ожидающую попытку.

## Окружение и границы

После зелёного gate локальная ara_dev мигрирована V6→V7. Все прежние описания колонок и счётчики строк совпали с началом, новая таблица пуста. Служебная первая попытка остановилась до миграции из-за порядка имён таблиц; после сравнения множества имён миграция завершилась. Содержимое пользовательских строк не читалось и не переписывалось. Preview остановлен и удалил только собственную QA-базу, агентская вкладка закрыта.

Итоговый снимок `.runtime/d03-04-final-runtime.json` совпал со стартовым `.runtime/d03-04-start-runtime.json` с единственными ожидаемыми отличиями: V7 и пустая таблица receipt. Ara_test пуста, временных ara_check_* осталось 0. PostgreSQL штатно остановлен с сохранением данных.

Прямая разработка на текущем Sol 6.1 High по выбранному пользователем варианту. Runner/tasks/progress, авторизация, провайдер/квота, старый storage/экспорт и прочие API не менялись. Чужие dirty-файлы сохранены, рабочий архив/output/.artifact-build не использовались. Секреты не нужны и не читались.

Ключ/текст неподтверждённой попытки удерживаются только в открытом UI. Восстановление после аварийного закрытия, автосохранение, undo/redo UI, вкладки, новые абзацы/структурные правки, реальный анализ и desktop-поставка остаются отдельными задачами. Ledger пока не очищается, иначе поздние повторы потеряли бы гарантию; политику жизненного цикла определить отдельно. После D03-04 следующая задача не запускалась.
