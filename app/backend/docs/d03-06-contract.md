# D03-06 — автосохранение выбранного фрагмента DOCX

30 октября 2026. Одна задача F05/F11 после D03-05; прямое продолжение здесь на Sol 6.1 High. Автоматически применить текущую ручную правку одного span через две минуты. Не добавлять ML, новые операции над Word, вкладки, историю, backend API или БД.

## Таймер

Чистый ES module autosave.js экспортирует AUTOSAVE_DELAY_MS=120000 и createAutosave({hasChanges,canSave,save,schedule,cancel,onError}). schedule/cancel — необязательные зависимости для проверки часов, по умолчанию setTimeout/clearTimeout. Импорт не ставит таймеров. Контроллер touch()/stop(): первый dirty-ввод заводит один таймер, последующий ввод не отодвигает его; deadline берёт последнее состояние. Без изменений не писать. Пока save выполняется, других save/таймеров этого контроллера нет. После завершения при оставшихся допустимых изменениях следующий срок — ещё 120000 ms; иначе таймер отсутствует до touch. Если временно busy/dialog, запись пропускается и проверяется через следующий интервал. stop отменяет timeout и запрещает старому уже попавшему в очередь callback писать/перевооружаться; контроллер другой правки независим. Исключение save не создаёт unhandled rejection и не оставляет running навсегда; уведомить onError. Авто- и ручная запись используют один общий busy guard.

В UI один контроллер на открытый draft, остановить при clearEditor/смене фрагмента/документа. Автоматически не писать unchanged, слишком длинный текст, восстановленный pending POST, конфликт копии/документа, paused error, неизвестную recovery state. Для обычного восстановленного dirty-черновика завести новый срок при явном открытии документа. На input после исправимой ошибки разрешить новый срок; конфликт документа требует переоткрытия. После потери ACK не запускать новую операцию таймером: оставить точный pending и кнопку ручного повтора D03-04/05. Никаких ускоряющих query/global/storage-флагов для QA.

## Сохранение и UI

Общий saveCurrent(automatic) использует прежнюю последовательность: stable operation UUID/payload → подтверждённый checkpoint D03-05 → POST text-edit с ключом → receipt → DELETE своей копии по CAS. Если checkpoint не подтверждён, POST не отправлять. Ошибки не затирают текст, не ребейзят stale anchor и не выдают чужую запись за успех. Тексты/ограничения backend неизменны. Receipt проверяется до изменения editor base: UUID документа, canonical string revision ровно expected+1 через BigInt, hex64 current hash, остальные прежние metadata. Никаких JS Number для ревизии.

На время авто-запроса ввод readOnly, но поле остаётся доступным для выделения/копирования и не теряет focus/caret; кнопки блокируются прежним busy guard. Это ограниченный первый вариант, параллельного набора во время записи нет. Успешное обычное автосохранение оставляет редактор открытым с тем же текстом/focus и обновляет expected revision/text/source SHA по **receipt этой операции**; path/part сохраняются, поскольку неизменный single-span exporter не меняет структуру. Установить новую clean base и убрать pending. Затем обновить список/структурный view, не вызывая clearEditor/openEditor и не теряя фокус. Новый view применять только при совпадении его revision/hash с receipt; иначе показать, что запись подтверждена, а просмотр не обновлён, остановить дальнейший timer и предложить переоткрытие. Не выводить новую ревизию из GET и не подменять ею CAS base.

При ошибке DELETE после подтверждённого POST оставить успех документа и предупреждение, закрыть панель как прежний manual save: следующую правку начать после явного переоткрытия. Не начинать новый checkpoint с неопределённым expected_token. Ручное сохранение сохраняет прежнее поведение закрытия панели. При 409/422/сети/timeout удержать текст и показать ошибку, автоматические повторы приостановить; при pending — ручной повтор тем же ключом. Не ослаблять подтверждение discard, beforeunload и dirty download guard. На экране указать интервал автосохранения и состояние результата, не выдавать сохранение копии за изменение DOCX.
