# D03-03 — ручная правка текстового фрагмента DOCX

30 октября 2026. Одна ограниченная задача после D03-02, часть F05/F10/F11/F12 текущего объёма. Выбор существующего text-span в UI → ручная замена его текста → явное сохранение в PostgreSQL → обновление просмотра/скачивание. Сохранять оригинал и нетронутое оформление через неизменный D02-03 export_docx и D02-06 save_docx. Прямая разработка в текущем чате, без Ralph/tasks/progress.

## API

POST `/docx-documents/{document_id}/text-edit`, только с DocumentRuntime. UUID — прежний HttpUUID, любые query-параметры — безопасный 422 до доступа к storage. JSON ровно из четырёх полей: expected_storage_revision (десятичная **строка**, canonical `[1-9][0-9]{0,18}`, 1..MAX_BIGINT-1), anchor, expected_text, replacement_text. Anchor ровно source_sha256 (lowercase hex64), part_name (1..1024 символа), path (list из 1..128 strict ints 0..100000, не bool). Тексты — strict str не длиннее 100000 Unicode code points каждый; без coercion/trim. Запретить extra/duplicate keys, NaN/Infinity и не-UTF8 JSON.

Content-Type application/json либо application/json; charset=utf-8 (регистр/внешние пробелы несущественны); Content-Encoding отсутствует/identity. Повторные Content-Type/Content-Encoding/Content-Length, неверная ASCII-длина или одновременные length/transfer-encoding — 422. Неподдерживаемый тип/encoding — 415 unsupported_media_type, message `Unsupported edit media type`. Поток ограничен **2 MiB**, заявленное превышение — до чтения, реальное — остановить до накопления лишнего chunk; 413 edit_request_too_large, message `DOCX edit request exceeds a technical limit`. Не использовать неограниченный request.body/Pydantic auto-body/multipart. Несовпадение заявленной длины и обрыв передачи — безопасный 422. Разбор JSON, валидация, ZIP/XML, DB и построение receipt — в threadpool после ограниченного чтения.

Получить неизменный stored snapshot через get_docx; проверить expected_storage_revision до экспорта. Превратить wire-anchor в SourceAnchor и применить один TextEdit через существующий export_docx. Сохранить полученные bytes через save_docx с той же ожидаемой storage revision. Между чтением/экспортом/сохранением другой writer может выиграть; обязательный финальный CAS предотвращает потерю его правок. Никаких новых транзакционных механизмов, изменения storage/БД или обхода ограничений signed/protected/tracked content.

EditError stale_source/text_mismatch — безопасный 409 с существующими code/message; invalid_anchor/unsupported_edit/invalid_input — 422; edit_limit_exceeded — 413. DocxError package_limit_exceeded и ProjectionError projection_limit_exceeded при экспорте — 413, остальные ошибки этих классов — 422. DocumentError storage/ownership/CAS проходит неизменным, другие неожиданные ошибки — безопасный storage_error 500. Ошибки не раскрывают текст/SQL/parser trace. При отказе до успешного save данные не меняются. Потеря подтверждения после commit может означать сохранённую правку; повтор со старой ревизией получает конфликт, автоматического overwrite/«успеха по совпадению текста» нет.

200 возвращает семь полей metadata как D02-07, но storage_revision — строка, точно до MAX_BIGINT. Receipt относится к snapshot успешного save, без дополнительного GET/view, bytes/anchors/owner/original hash не возвращаются. Cache-Control no-store. Свежая валидная no-op правка всё равно использует save_docx и увеличивает storage revision, bytes остаются точными; UI не отправляет неизменённый текст. OpenAPI документирует строгий JSON, строковую ревизию, ограничения и ошибки 404/409/413/415/422/500/503. Старые OpenAPI wrappers/контракты неизменны.

## Интерфейс

Проецируемые text-spans становятся отдельными доступными с клавиатуры кнопками выбора, включая текст внутри таблиц/гиперссылок. Пустой text-span обозначить нейтрально. Выбор открывает подписанное поле с исходным текстом и действия «Сохранить правку»/«Отменить правку». Не делать contenteditable всему документу и не обещать новые абзацы/переносы, структурные изменения или полную вёрстку Word. Непоказанные элементы остаются read-only; допустимость реального изменения проверяет существующий экспорт. Для слишком длинного span оставить просмотр. В UI явно указать границы правки одного фрагмента и отсутствие новых переносов.

Draft удерживает document_id, исходную строковую storage revision, anchor и expected_text из одного view. Не преобразовывать ревизию в JS Number. Не отправлять изменённый текст при выборе/вводе, только по явному сохранению. Кнопка сохранения неактивна для unchanged/слишком длинного текста; duplicate clicks и параллельные операции блокируются. Импорт/выбор файла недоступны при открытой правке. При переключении документа/фрагмента с dirty-текстом спросить подтверждение удаления именно локальной правки; отмена оставляет её. beforeunload защищает dirty-текст. Обновление списка не уничтожает draft. Скачивание при dirty-тексте заблокировать с понятным предложением сначала сохранить/отменить, чтобы не выдавать старый файл за изменённый.

После 200 закрыть draft, обновить metadata/список/view. Ошибка последующего чтения не отменяет подтверждённое сохранение. При 409/422/сети/тайм-ауте textarea и исходный draft сохраняются, сообщение объясняет отказ/неподтверждённое сохранение; не выполнять принудительную запись или автоматическое обновление view с потерей текста. При конфликте пользователь может скопировать текст и явно переоткрыть документ с подтверждением. При отмене draft ничего не писать в БД. Все строки через textContent/DOM API; без localStorage/sessionStorage, внешних ссылок, AI-правок, таймера, истории undo/redo UI и новых зависимостей.
