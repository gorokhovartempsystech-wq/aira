## Запрос

Все перечисленные поля обязательны. Пустой массив используется, если элементов нет. Неизвестные поля отклоняются валидатором этой версии.

| Поле | Тип | Правило |
|---|---|---|
| contract_version | string | Ровно 0.1.0 |
| run_id | string | Непустой ID задания, назначает backend |
| mode | string | lint или merge |
| base_document | object | document_id, version_id, blocks |
| context | object | revision_id, items |

Все ID — непустые непрозрачные строки. Содержимое версии документа и ревизии контекста неизменяемо. Пользовательские права определяет backend; модель не выбирает владельца или доступные документы.

Блок base_document.blocks: id, kind, text. kind: heading, paragraph, list, table, code, unsupported. text — точная строка представления блока, для поддержанных типов — Markdown. ID уникален внутри данной версии. Содержание таблицы или блока кода не сворачивается в обычный абзац. Для unsupported передаётся описание пропуска; оригинал хранится отдельно и недоступен для автоматической замены. Первая реализация может принимать только текст/Markdown, не заявляя импорт Word/PDF.

Элемент context.items: id, role, text. role: new_requirement, user_clarification, reference. ID уникален внутри ревизии контекста. В merge нужен минимум один new_requirement; в lint их нет. Первая версия допускает один целый текст нового требования как один элемент; атомарное разбиение на требования не считается достоверным только потому, что его предложила модель.

Контекст содержит только явно выбранные материалы. Ответ на уточняющий вопрос сохраняется как новая ревизия контекста и запускает новое задание. Старый результат не переписывается. Текст документов рассматривается как данные: инструкции из него не дают модели разрешения выполнять инструменты, обращаться к сети или менять исходники.

## Результат

| Поле | Тип | Правило |
|---|---|---|
| contract_version, run_id | string | Совпадают с запросом |
| base_version_id, context_revision_id | string | Совпадают с конкретными входными версиями |
| review_status | string | ready либо needs_clarification |
| summary | string | Краткое описание результата |
| coverage | array | Учёт каждого входного блока и элемента контекста |
| findings | array | Замечания |
| change_groups | array | Группы предлагаемых правок |
| questions | array | Неразрешённые вопросы |
| change_outcomes | array | Учёт каждого new_requirement; в lint пусто |

ready означает, что в ответе нет вопросов. Он не означает принятия правок, полноты проверки или доказанной правильности. При непустом questions требуется needs_clarification. Технически успешный результат может содержать вопросы и пропущенные блоки.

### Ссылки и полнота проверки

Evidence: source (base/context), id (ID блока/элемента), quote (непустая точная подстрока его text). Координаты вывода вычисляет backend. Нельзя ссылаться на текущую последнюю версию вместо версии запроса. Текст цитаты и существование источника проверяются программно; смысловая правильность такого доказательства этим не подтверждается.

Coverage entry: source, id, status (analyzed/skipped), reason (null для analyzed; непустая строка для skipped). Каждая входная ссылка присутствует ровно один раз. Неподдержанные блоки всегда skipped. Backend формирует признак неполной проверки по coverage и данным импортера. Модель не может отменить известный импортеру пропуск. Пропущенные новые требования нельзя показывать как обработанные.

### Замечания

Finding: id, category, severity, assessment, title, explanation, evidence. Все строки непустые, evidence содержит минимум одну ссылку.

- category: ambiguity, contradiction, duplication, unverifiable, contract_mismatch.
- severity: info, warning, critical. Это предлагаемый приоритет внимания, а не доказанная серьёзность дефекта системы.
- assessment: observed_inconsistency или needs_confirmation.

У противоречия нужны минимум два разных подтверждающих фрагмента. Разные числа без несовместимых условий не считаются достаточным обоснованием. Численный confidence не предусмотрен: его нельзя без оценки объявлять вероятностью правильного ответа.

### Предлагаемые изменения

Change group: id, title, basis, rationale, evidence, depends_on_group_ids, blocking_question_ids, patches.

basis: explicit_requirement или design_proposal. Это разделяет перенос явного требования и предложенный моделью способ реализации. evidence и patches непустые; остальные массивы могут быть пустыми. ID групп уникальны. Зависимости должны существовать, не образовывать циклы и не ссылаться на себя.

Patch: operation, target_block_id, new_blocks. Все операции адресуют только блоки базовой версии:

| operation | new_blocks |
|---|---|
| replace_block | Один или несколько новых блоков вместо целевого |
| insert_before / insert_after | Один или несколько блоков перед/после целевого |
| delete_block | Пустой массив |

Новый блок содержит kind и text. Допустимы только поддержанные kind, кроме unsupported. Новые ID назначает backend при создании версии. Значения title/rationale/evidence не являются командами для применения правок.

Решение относится к группе целиком. Реализованный Review API позволяет редактировать тексты существующих new_blocks, сохраняя правки отдельной ревизией решений; исходный результат остаётся доступен. Интерфейс редактирования и preview ещё не реализованы. Если пользователю нужны независимые правки, модель должна предложить отдельные группы.

Валидатор результата запрещает замену или удаление unsupported-блока. На этапе preview/apply backend должен запрещать пересекающиеся записи в один блок и удаление якоря вставки в выбранном наборе. Порядок независимых вставок фиксируется порядком групп и операций результата и будет показан в preview. Конфликтующие альтернативы допустимы в результате и сохранённом черновике решений, но не для совместного применения.

### Вопросы и судьба нового требования

Question: id, prompt, reason, evidence. Все обязательны, evidence непустой. Ссылка blocking_question_ids блокирует применение зависимой группы. Ответ пользователя добавляется в контекст нового запуска. Простое снятие флага вопроса без новой ревизии результата не разблокирует прежнюю группу.

Change outcome: context_item_id, status, rationale, change_group_ids, question_ids, evidence. На каждый new_requirement ровно один outcome.

status: proposed, already_satisfied, needs_clarification, out_of_scope. proposed означает наличие предложений, а не применение. already_satisfied требует ссылки на базовый документ. needs_clarification требует хотя бы одного вопроса. out_of_scope требует объяснения и остаётся видимым, пользователь может оспорить вывод. Принятие, отклонение и отложенное решение пользователя хранит backend отдельно.

## Обязательные проверки backend

Проверки формы и ссылок уже выполняются при сохранении результата и чтении review. Проверки применимости выбранного набора и новой версии относятся к следующим циклам T03-02/03.

1. Схема типов, обязательные поля, enum, уникальность ID и совпадение версий/задания.
2. Существование evidence и буквальное совпадение quote.
3. Полный учёт входов в coverage; запрет фиктивной проверки unsupported.
4. Полный учёт new_requirement; корректность ссылок на группы/вопросы.
5. Корректность операций, зависимостей, блокирующих вопросов и выбранного набора.
6. Перед применением новой версии — доступ пользователя, версия документа, ревизия решений и идентификатор preview.

Невалидный ответ модели не сохраняется как успешная проверка. Worker записывает техническую ошибку и применяет ограниченную политику повторов. Ошибка транспорта/провайдера находится вне схемы смыслового результата; модель не генерирует статус авторизации или технический HTTP-ответ.

Версию адаптера, модель, конфигурацию/промпт, длительность, идентификатор попытки и фактическое потребление ресурсов фиксирует worker по выполнению. Эти сведения не берутся на веру из текста модели. Для заглушки backend возвращает явный execution_mode: fixture; для подключённой модели — model.

Формальные модели и проверки отрицательных случаев завершены в [T02-01](../docs/t02-01-result.md). `validate_result` проверяет буквальные ссылки, полноту coverage/outcomes и зависимости, а также вычисляет `incomplete_review` из skipped и доверенного флага импортера. JSON Schema описывает форму; междокументные ограничения выполняет валидатор. Результат без замечаний допустим. Совпадение цитат не доказывает истинность вывода, а прохождение контракта не означает качество ML. [T02-02](../docs/t02-02-result.md) сохраняет задания, [T02-03](../docs/t02-03-result.md) выполняет fixture и сохраняет проверенный результат.

В [T03-01](../docs/t03-01-result.md) завершены GET/PUT `/runs/{run_id}/review`: виртуальная ревизия 0 без записи, полный снимок решений `pending`/`accepted`/`rejected`/`deferred`, точные текстовые edits и неизменяемая история. Оба метода возвращают ReviewResponse из 11 полей; optional `revision_id` в GET выбирает историческую ревизию. PUT сверяет ожидаемого родителя и SHA-256 fingerprint исходного результата, повтор того же снимка возвращает прежнюю ревизию. Это отдельный HTTP-контракт, исходные AnalysisResult и RunResponse не меняются. `accepted` сохраняет намерение, даже если остаются вопросы или непринятые зависимости; оно не означает применение.
