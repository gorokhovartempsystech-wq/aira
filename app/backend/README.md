# AI Requirements Assistant

Первая цель: проверить спецификацию, внести новое требование через просмотр правок и сохранить новую версию. Основные направления — Linting и Merge; первая интеграция — Confluence Data Center.

Есть backend с `/health`, `/me`, PostgreSQL, версиями документов и сохраняемыми заданиями Linting/Merge. Отдельный worker выполняет тестовый сценарий и сохраняет проверенный результат, умеет повторять потерянные попытки и отклоняет запоздалые ответы. Через Review API можно сохранить выбор групп, отредактировать текст предложений и прочитать историю решений. Пока используются явный fixture и локальный тестовый пользователь. Preview, apply, реальный ML, настоящий вход, интерфейс и Confluence ещё не реализованы.

## Локальная разработка

```bash
bash scripts/bootstrap.sh
bash scripts/postgres.sh start
bash scripts/check.sh
bash scripts/dev.sh --documents
```

`bootstrap.sh` создаёт `.venv` и устанавливает зафиксированные зависимости из `requirements.lock`. Нужен Python 3.12 или 3.13; нестандартный путь можно передать через `ARA_PYTHON`. В этой рабочей папке используется Python 3.12 из установленного Codex runtime. `dev.sh --documents` поднимает API на `http://127.0.0.1:8000`, интерактивная документация — `/docs`. В ней можно выполнить POST /documents с title и content_markdown, затем прочитать список и сохранённую версию.

Команда `--documents` явно выбирает подготовленную локальную peer-БД ara_dev без пароля. Она задаёт ARA_ENVIRONMENT=local только процессу сервера и создаёт при startup синтетического пользователя с проектом; повторный запуск их не дублирует. При уже указанном нелокальном окружении запуск отклоняется. Эта специальная команда не использует внешнюю ARA_DATABASE_URL и не запускает миграции. Для одного `/health` без БД по-прежнему доступна `bash scripts/dev.sh` без аргументов. Порт меняется через ARA_PORT, host остаётся 127.0.0.1.

Локальный PostgreSQL описан в [инструкции окружения](docs/local-postgres.md). Он установлен в игнорируемой папке `.runtime`; миграция `0004_review_revisions` применена к `ara_dev` с сохранением прежних строк, повторный upgrade проверен. Результат — в [отчёте T03-01](docs/t03-01-result.md). Общая проверка требует работающей БД, создаёт собственные одноразовые базы и удаляет их после тестов. `ara_dev` и `ara_test` она не очищает. После работы остановить БД: `bash scripts/postgres.sh stop`. Для `/health` запуск БД не нужен.

Проверки используют настоящую PostgreSQL: проверяются точный текст и блоки после пересоздания приложения, неизменяемая история, границы доступа, безопасные ошибки и полный откат при отказе записи/commit. Две конкурентные записи версии с одной базой дают один успех и один конфликт. Для review одинаковые конкурентные сохранения возвращают одну ревизию; разные решения от одного родителя дают один успех и один конфликт. Два предупреждения deprecation относятся к зависимостям TestClient.

Отдельный запуск на `127.0.0.1:8013` подтвердил `/health`, `/me`, `/documents`, OpenAPI с GET/PUT review и ответом из 11 полей, безопасный 404 обоих методов для неизвестного run. Новые документы и задания в `ara_dev` не создавались. После проверки HTTP и PostgreSQL штатно остановлены, одноразовых тестовых баз не осталось, `ara_test` пуста.

Завершены **T01-01** ([каркас](docs/first-ralph-cycle.md)), **T01-02** ([PostgreSQL и миграции](docs/t01-02-result.md)), **T01-03** ([API документов](docs/t01-03-result.md)), **T01-04** ([история версий](docs/t01-04-result.md)), **T02-01** ([контракт анализа](docs/t02-01-result.md)), **T02-02** ([сохраняемые задания/API](docs/t02-02-result.md)), **T02-03** ([worker и fixture](docs/t02-03-result.md)) и **T03-01** ([ревизии решений](docs/t03-01-result.md)). T03-01 выполнен за одну итерацию Ralph; независимая проверка — **468 тестов и 24 подтеста проходят**, Ruff и форматирование проходят.

До полного технического сценария через API с fixture остаются два цикла: **T03-02 — preview и diff**, **T03-03 — применение новой версии**. До пилота остаются шесть крупных этапов бэклога: оставшаяся часть T03, T04–T08. Технический сценарий сам по себе не подтверждает качество ML или готовность пилота.

Пакет `ara.analysis_contract` проверяет запрос и результат по версии 0.1.0: типы, версии, буквальные цитаты, coverage, outcomes, зависимости и допустимые операции. `validate_result(payload, request=request, has_import_omissions=False)` возвращает проверенный result и вычисленный backend признак incomplete_review. Он работает без БД, файлов и сети, не выполняет анализ текста сам. [JSON Schema и описание](contracts/README.md) предназначены для будущего адаптера.

Задание создаётся через `POST /documents/{document_id}/runs`: обязательный единственный заголовок `Idempotency-Key` и тело с `mode`, `base_version_id`, `context_items`. В `/docs` можно передать сохранённую версию документа и, например, контекст `[{"id":"req-1","role":"new_requirement","text":"Сохранять имя устройства при переименовании комнаты."}]` для `mode=merge`; для lint допустим пустой список. Ответ 202 содержит `run_id`, неизменяемый `request`, `status=queued` и `execution_mode=fixture`. HTTP сам не запускает worker.

В другом терминале обработать одно задание:

```bash
bash scripts/worker.sh --once
```

Для постоянного опроса очереди: `bash scripts/worker.sh`, остановка Ctrl+C. После выполнения `GET /runs/{run_id}` возвращает `status=succeeded`, `result`, `incomplete_review` и `attempt_count`; при технической ошибке — `status=failed` и безопасный `error`. Повтор POST возвращает актуальное состояние прежнего задания. Ошибка адаптера допускает ограниченный повтор; невалидный результат становится terminal-ошибкой. `needs_clarification` внутри валидного результата остаётся успешным выполнением.

Fixture воспроизводимо предлагает вставить точный текст новых требований после последнего поддержанного блока. При отсутствии якоря возвращает вопросы, для lint — пустой демонстрационный список замечаний. Это проверка технического сценария, не смысловой анализ документа. Выполнение и ответы явно помечены fixture; вызовов модели нет.

Для успешного задания `GET /runs/{run_id}/review` читает текущие решения. До первого сохранения это виртуальная ревизия 0: все группы `pending`, записей в БД не создаётся. `PUT` по тому же пути сохраняет полный снимок: `expected_revision_id`, `expected_result_fingerprint` из GET и `decisions` для каждой группы ровно один раз. Доступны `pending`, `accepted`, `rejected`, `deferred`; в `edits` можно задать точный текст существующего new_block по `patch_index` и `new_block_index`, включая пустую строку.

Общий ответ GET/PUT содержит ровно 11 полей: `run_id`, `document_id`, `base_version_id`, `context_revision_id`, `execution_mode`, `revision_id`, `parent_revision_id`, `revision_number`, `created_at`, `result_fingerprint`, `decisions`. `GET /runs/{run_id}/review?revision_id=<UUID>` читает сохранённую историческую ревизию. Старый ответ `GET /runs/{run_id}` сохраняет прежние 14 полей.

`accepted` фиксирует намерение пользователя: черновик может содержать блокирующие вопросы, непринятые зависимости и конфликтующие альтернативы. Проверка применимости относится к будущему preview/apply. Сохранение сверяет ожидаемого родителя и fingerprint результата; устаревший изменённый черновик получает 409, точный повтор возвращает уже созданную ревизию. Результат анализа и версии документа остаются неизменными. [Контракт Review API](docs/t03-01-contract.md).

Worker по умолчанию выдаёт аренду на 30 секунд, допускает 3 попытки и фиксирует общий срок 900 секунд с первого захвата; задержка повтора — 1 секунда. Флаги: `--lease-seconds`, `--max-attempts`, `--run-timeout-seconds`, `--retry-delay-seconds`, `--poll-seconds`. Лимит попыток и deadline уже начатого задания не меняются новой конфигурацией worker. Истечение аренды запрещает запись, но не прерывает зависший вызов; восстановление выполняет следующий проход worker. [Точный контракт выполнения](docs/t02-03-contract.md).

Локальный launcher использует только собственную peer-БД ara_dev, не запускает PostgreSQL/миграции и отказывается от явно нелокального окружения. `.venv/bin/python -m ara.worker --once` — вариант с явными ARA_ENVIRONMENT=local и ARA_DATABASE_URL через существующий загрузчик настроек. Импорт worker не читает настройки и не запускает работу.

Повтор с тем же ключом и содержимым возвращает прежнее задание; изменение версии, контекста, режима или документа с тем же ключом даёт 409. При одновременных запросах остаётся один run/context. Снимок переживает пересоздание приложения и не меняется при появлении новой версии документа. Доступ проверяется по текущему владельцу проекта и создателю задания. [Точный контракт API и ограничений](docs/t02-02-contract.md).

Создание следующих версий пока доступно разработчику через `ara.documents.storage.append_version(runtime, document_id=..., expected_version_id=..., content_markdown=...)`. Функция возвращает сохранённый снимок или безопасную ошибку; устаревшая база даёт `version_conflict`. Отдельного HTTP endpoint записи версии нет: будущий Merge/apply будет использовать этот слой. GET /me показывает серверные user_id/project_id и local/local-dev; попытка собрать локальный HTTP-runtime при явно нелокальном ARA_ENVIRONMENT отклоняется. Это техническое ограничение dev-режима, не настоящий вход.

Запуск одной задачи и критерии завершения описаны в [инструкции Ralph](docs/ralph-usage.md). Runner ограничен тремя попытками и не переходит к следующим задачам автоматически. Для этой машины подготовлен совместимый [локальный CLI](docs/cli-runtime.md). Повторный запуск завершённой задачи не обращается к модели.

## Основания

- [Границы MVP и разбор прототипа](docs/mvp-scope-draft.md).
- Классификация устройства: уточнённый кейс (локальный материал, не входит в пакет).
- Черновые кейсы оценки (локальный материал, не входит в пакет).
- Выборочный разбор рабочего архива (локальный материал, не входит в пакет).

В локальной разработке секреты загружаются только из ~/secrets.env. В файлах проекта хранятся имена настроек без секретных значений.

Для явного запуска миграций используется `.venv/bin/python -m alembic upgrade head`. Он требует `ARA_DATABASE_URL` с драйвером `postgresql+psycopg`; настройка читается из окружения процесса или `~/secrets.env`, значения скрываются в представлении настроек и ошибках валидации. Для локального peer-подключения пароль не нужен, каталог сокета выводит `scripts/postgres.sh start`. Импорт приложения не читает настройки и не применяет миграции.
